# Security and privacy

DataCanvas is a local tool: it runs on your computer, talks to your database from your computer, and sends nothing anywhere else. This page says exactly what that means, and what it does not.

> DataCanvas has not had an independent security review. Nothing here is a guarantee that it is "completely secure". Please read the limits at the end.

## What stays on your machine

| Thing                            | Where it lives                                                                                                                                                                                                                                                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Database password                | In memory of the running server only. Never written to disk, never returned by the API, never logged.                                                                                                                                                                                                    |
| Host, port, database, user       | In `~/.datacanvas/connections.json` only if you choose **Save connection**, together with whether data viewing is on. Not the password.                                                                                                                                                                  |
| Table rows (if you view data)    | In the memory of the server for the length of one request, and in your browser's memory while a table's Data section is open. Never written to a file by DataCanvas: the one exception is a file you ask for with **Export**, which your browser saves on your computer and DataCanvas keeps nothing of. |
| SQL drafts, results, and history | In browser memory, and on the local server for the duration of a request.                                                                                                                                                                                                                                |
| Saved SQL queries                | Names and SQL text you explicitly save. Owner-only files for saved profiles under `~/.datacanvas/saved-queries/`, or server memory until an unsaved connection closes.                                                                                                                                   |
| A change you preview (writes)    | The planned statement and its values in the server's memory for at most five minutes, until it is applied or dropped. Never written to a file or logged.                                                                                                                                                 |
| An import you preview (writes)   | The rows of the file, in your browser while the import dialog is open, and in the server's memory with the planned statements for at most five minutes, until applied or dropped. The file itself is never sent, saved or logged; the server never parses it.                                            |
| The list of changes made         | In the server's memory for the session: the kind of change, the table, the column names, the time and the outcome (and the statement for a change of structure, left out when it carries a default value or a comment you typed). Never row values, never a file.                                        |
| Canvas layouts                   | `~/.datacanvas/workspaces/` (table names and positions). Files are owner-only (mode 0600).                                                                                                                                                                                                               |
| Session token (while running)    | In the server's memory and in `~/.datacanvas/run.json` (owner-only) so a second launch can reopen it. Deleted on exit.                                                                                                                                                                                   |
| What leaves the machine          | Nothing. No account, no cloud, no analytics. Telemetry of the web framework is switched off at start-up.                                                                                                                                                                                                 |

Set `DATACANVAS_HOME` to use a different folder.

## What DataCanvas reads from your database

By default, only **metadata**: schema, table and column names, types, keys, indexes, constraints, comments, definitions of views, functions and policies, usage counters and row-count estimates. Every query runs in a read-only transaction, and SQL you write runs only in the SQL tab (below).

If you switch on **data viewing** for a connection (off by default, shown by a badge, remembered with the saved connection), DataCanvas also reads **rows**: a `SELECT` on a table you open, in the same read-only transaction, with limits on rows, columns, cell length, response size and time. It has a small set of fixed shapes: a sort and up to three conditions are structured choices from the screen (a column, a fixed operator, a value), never text you write, and every value is sent to the database as a parameter, so the Data tab itself never runs SQL you write. A sort or a condition on a hidden column is refused until you reveal it, because it would reveal the column one question at a time. Rows go from the database to the local server to your browser and nowhere else; they are never written to a file by DataCanvas, logged, cached, or included in an error message, a snapshot or a workspace (a result you save from the SQL tab, below, is a file you make yourself). Columns whose names look sensitive (`password`, `token`, `secret`, ...) are not sent unless you reveal them; this is a convenience, not a security control, because names are only a hint. Anyone who holds the session token can switch data viewing on, so treat the printed link like a password.

## When DataCanvas changes your database

Never by default. Changing rows or structure (1.4.0) needs **all three** of:

1. DataCanvas was **started with `--enable-writes`**. The switch is a command-line flag, not something the app or the API can turn on, so a web page or a program that gets hold of the session token still cannot enable it. An environment variable in your shell does not count either; only the flag does. DataCanvas prints a notice at every start with the flag.
2. The connection is to a database **on this machine**: its host is `localhost`, an address in `127.0.0.0/8` or `::1`. Everything else stays read-only.
3. You **unlock writes for that connection** by typing its database name. The unlock is kept in memory only, is never saved with the connection, and ends when you disconnect, reconnect or stop DataCanvas. Viewing table data must also be on.

Even then the SQL tab stays read-only, and a change is a structured operation (a table, a key, a column and a value; or a column definition from fixed lists of types and defaults), the server builds the statement from names checked against the catalog, and every value is sent as a parameter. You see the exact statement before it runs; applying runs exactly that statement, in one transaction, with a 3 second limit on waiting for a lock. A row change must change exactly one row. An update is refused if a column you changed no longer holds the value you saw; other columns are not compared, so two people changing different columns of one row do not conflict, and a delete is by key and compares no values. DataCanvas itself never uses `CASCADE`: a drop is refused while a view, a foreign key or an index depends on it. A foreign key that already cascades or sets NULL still does so when you delete a row, and the preview names it. A database error never reaches the screen as is (it can contain a value); you get a fixed sentence that may name a constraint or a column.

## The SQL tab (1.6.0)

Off unless **data viewing** is on for the connection (a result is rows). It is the one place where text you type becomes SQL, so it is narrow:

- **One statement, read-only.** The statement runs in a read-only transaction on a connection opened for that run and closed after it, never one of the pool, so it cannot change what a later write does. PostgreSQL refuses more than one statement in a text. It cannot write, even when DataCanvas was started with `--enable-writes`.
- **What it starts with.** The first word must be `SELECT`, `WITH`, `VALUES`, `TABLE`, `EXPLAIN` or `SHOW`, checked the way PostgreSQL reads comments and white space. This keeps out what a read-only transaction does not stop (`DO`, `COPY ... TO PROGRAM`, `CALL`, `SET`, `BEGIN`), and `EXPLAIN` is allowed only for a plain query without the word `INTO`, because PostgreSQL runs `EXPLAIN ANALYZE CREATE TABLE ... AS` without its read-only check.
- **Limits.** 1,000 rows by default (10,000 at most), read in small batches and stopped at 64 MB, a 30 second time limit (5 minutes at most), one statement at a time per connection, and Cancel really cancels it in the database. A single very large value is still read whole before it is cut, so a statement that returns half a gigabyte in one cell can use that much memory.
- **Masking does not apply.** A query can rename or compute any column, so hiding columns by name cannot work here. It shows what the connected role can read; **the role is the control**.
- **Your database role matters most here.** A read-only transaction stops every write, but not what a function can do outside the database. A superuser, or a role that may run programs or read files on the database server, can do that from a `SELECT`. The SQL tab says so above the editor for such a role. Use a read-only role for SQL you did not write yourself.
- **Drafts, results, and execution history** stay in memory and are dropped when you close the page or disconnect. DataCanvas logs none of them. A database error about your statement is returned to you with its position. Exporting a result creates a file of your rows at your request.
- **Saved queries** keeps only the name and SQL text you explicitly save, including any literals typed into the query. DataCanvas stores saved-profile libraries in `saved-queries/` under its local data folder, with owner-only permissions on systems that support them. Unsaved connections use server memory. Saving a connection also keeps its saved queries with the profile. Forgetting a saved profile removes its library. The library uses the local app session and the connection's data-viewing switch. Opening a saved query loads the editor. Execution still requires **Run**.
- **Completion** uses the names of your database that the app already reads (tables, columns, functions), kept in memory. Nothing is sent anywhere for it, and the editor is built into the package: it loads nothing from another host.

**What "on this machine" cannot prove.** The host is what you typed. An SSH tunnel (`ssh -L`) or the Cloud SQL Auth Proxy listens on `127.0.0.1` and forwards to a remote, possibly production, database, so such a connection looks local. The unlock dialog shows the address the database server reports and asks you to make sure it is not production, and a red **Writes on** badge stays visible while writes are unlocked, but neither is proof. A committed change cannot be undone.

**Your database role.** DataCanvas warns when the role you connected with can do more than the task needs: when browsing, a role that can change data or create objects; with writes unlocked, a superuser or a role that can create roles or databases, bypass row-level security or reach the server's files. The warning never blocks you.

## Migrations (1.7.0)

The **Migrations** tab writes SQL as **text** and runs none of it: there is no new route, no connection of its own and no way to apply a script from DataCanvas. It is built in your browser from the structure of the two sides (a snapshot or a live read of the structure), so it holds no rows and saves nothing.

- **The text is the risk.** A script is made from names and definitions read from a database, which may be hostile. Every name goes through identifier quoting and every literal through string quoting (a backslash becomes an `E''` string); definitions PostgreSQL printed (`pg_get_constraintdef`, `pg_get_viewdef`, `pg_get_functiondef`) are used as printed. Comments are cut to one line, at carriage returns as well as line feeds. Held (unconfirmed destructive) SQL is written as comments line by line. Tested with names made of quotes, line breaks, `;`, `--`, `/*`, `$$`, emoji and 63-byte names, by running the result on a real PostgreSQL.
- **Run what you have read.** A migration contains the **text of views and functions** read from the databases it compares, and running it runs that text. A function or view in a database you do not control can do anything its definition says. Each file says so at the top.
- **Formats.** A dbmate or goose file is refused when a name or text in the migration holds a line that the runner would obey (`-- migrate:`, `-- +goose`). Flyway reads `${...}` as a placeholder; a file with that text says so.
- **What it does not know.** It compares structure, not data, owners, grants, partitioning, storage options, view options or the position of a sequence, and says so in every migration. A rename is only ever applied when you confirm it, and the text of functions is not rewritten for one.
- **Destructive changes** (drops, a column type that loses data) are flagged, and each needs its own confirmation before it is more than a comment. A rollback cannot bring back rows that a drop removed.

## How the local server is protected

A web page you visit can try to reach programs listening on `127.0.0.1`. DataCanvas defends against that in layers:

1. It listens on `127.0.0.1` only, never on your network. (The one exception is a container, 1.11.0: `--host 0.0.0.0` is refused unless `DATACANVAS_ALLOW_ANY_INTERFACE=1` is set, which only the Docker image does, because a published port reaches the program through the container's own interface. Every other layer below still applies, so a request that arrives through a LAN address is refused; publish the port to `127.0.0.1` of the host only, see `docs/docker.md`.)
2. **Host check** (blocks "DNS rebinding"): only `127.0.0.1:<port>` and `localhost:<port>` are accepted.
3. **Origin check**: state-changing requests from another web page are refused. The browser's `Sec-Fetch-Site` hint must say same-origin.
4. **Session token**: every start creates a new random secret. The link printed by `datacanvas` carries it once; the app swaps it for an `HttpOnly`, `SameSite=Strict` cookie and removes it from the address bar. Requests without it are refused. Treat the printed link like a password while DataCanvas runs.
5. The checks run in the front door (`proxy.ts`) **and** again inside every API route.
6. No CORS headers are ever sent, so other sites cannot read responses. Responses forbid framing and referrers.
7. **A Content-Security-Policy with a nonce made for each page request** (1.10.0): a script runs only when it carries that nonce (the framework's scripts and our one script), nothing runs from inline text, an inline handler or `eval`, and the page may connect only to its own server. So text that ends up in a page (a table name, a value) cannot run as a script even if a component forgot to escape it. Styles keep `'unsafe-inline'` (the canvas and the menus set `style` attributes, which a nonce cannot cover; no code runs from a style). Every end-to-end test of the project fails when a page breaks the policy.
8. **The door for Claude (1.11.0) is separate** and does not exist while nothing is shared (404). `POST /mcp` takes only a token of its own (`Authorization: Bearer`, made for each run, never the session token, compared in constant time) and the same Host check; it refuses any request that carries an `Origin` or a `Sec-Fetch-Site` header (a web page), sends no CORS headers, and is never reachable with the browser's cookie. The token of `/mcp` is no credential for the app either: the cookie guard never reads an `Authorization` header. The token is written, with the port, to `mcp.json` in your data folder (mode 0600) for the bridge `datacanvas mcp` to find.

## What to do for your database

- Use a **read-only database user** with the least access that is useful. If you edit with DataCanvas, use a role that can change only the tables you mean to change, on a local development database.
- Use **TLS with certificate verification** when the database is not on your own machine.
- DataCanvas sets connection and statement timeouts and limits the size of everything it reads.

## Statistics, documentation exports, chosen rows and plans (1.10.0)

None of these writes to a database.

- **Statistics** (the table details) come from the server's own figures: the share of NULLs, the number of distinct values, the width and the order of each column, the sizes, and when the table was last vacuumed and analysed. **No row and no value is read:** the statistics that hold values of the table (the most common values, the histograms) are never selected, and a test fails if any statement names one. They need no "Allow viewing table data", like the row-count estimate.
- **Export documentation** makes a Markdown, Mermaid, DBML or PlantUML file in your browser from table, column, key and index names and their types (the Markdown file and DBML also carry column defaults, check rules and comments, which can hold a literal). No row of any table is read, nothing is uploaded, and every name is quoted for its format so a name cannot become syntax. The names can reveal how your system works: check where you paste a text diagram.
- **Export chosen rows** reads the rows you chose again on the server, each by the table's whole key (up to 500), with the same rules as any export: a hidden column is left out, a value is read whole, the data-access check comes first. A key column that looks sensitive and was not shown, a table without a key and a key that is not the table's key are refused. The notes of the file say how many rows were chosen, never their keys.
- **A script of INSERT statements** is text you run yourself: every value a quoted text literal, every name quoted, in one transaction. A script that was cut ends with `ROLLBACK;` instead of `COMMIT;`, and one that failed has no `COMMIT;`, so a half script commits nothing. Run it in a test copy first.
- **The query plan viewer** reads the plan of your own statement (JSON) as untrusted text with limits, shows it in the tab, and keeps it nowhere (the statement is in the tab's history, like any statement that ran).

## Letting Claude read a connection (1.11.0)

Off until you press **Share with Claude** under a connection. Nothing in it writes to a database, to a file or anywhere else: there are thirteen tools and a test pins the list.

- **What it is.** The Claude app you already use (Claude Desktop, Claude Code, any MCP client) asks DataCanvas on this machine for things to read, and DataCanvas answers. DataCanvas holds no API key and calls no cloud service. **What Claude reads is sent to Anthropic by the Claude app, and DataCanvas cannot stop that or take it back.** Share only what may leave your machine, and use a database user that cannot read the rest.
- **Two levels**, per connection, kept in memory only (never saved with a profile, a workspace or a snapshot; gone on a restart, on a disconnect, and when viewing table data is switched off). **Structure**: names, types, keys, indexes, foreign keys and the server's statistics, no row. **Structure and data**: also pages of rows and read-only queries, which needs **Allow viewing table data**.
- **You approve each data call** (on by default; you can turn it off): the call shows you what Claude asked and nothing runs until you press Approve; Escape does not answer; after two minutes it is refused. **Pause** refuses every call at once. At most 30 calls a minute are served. A list shows what Claude asked and how it ended, with counts, never a value that came back. Claude cannot answer or pause itself: those routes need the browser's cookie.
- **Reads only.** Statements run through the SQL tab's runner (a read-only transaction on a connection of its own, one statement, the statement and row limits); pages through the page reader. `EXPLAIN` is not run with `ANALYZE`.
- **Hidden columns are a safety net, not a barrier.** A column whose name looks sensitive (`password`, `token`, `secret`, ...) is left out of the rows DataCanvas hands to Claude, is never sorted or filtered on, a statement that names one is refused, and in a result such a column is NULL. But a name is only a hint, and a model that is told to can get around it: a whole-row value (`row_to_json(t)`, `t::text`), renaming the columns of a table (`FROM t AS x(a, b, c)`), a view that renames a column, or a column whose name is not on the list (`hashed_pw`, `ssn`). The statistics catalogs (`pg_stats`, `pg_statistic`) and `pg_stat_activity` are refused, as are functions with an effect outside the data (`pg_notify`, advisory locks, `dblink`, large objects). The control is a database user that cannot read what must not leave.
- **What the structure level also returns.** Column defaults, comments and check definitions (they can hold a literal); for a hidden column they are left out.
- **What a read-only transaction still allows.** A statement can sleep for up to its time limit (30 seconds at most), take shared locks, and use the one statement slot that the SQL tab also uses, so the SQL tab can answer "busy" while Claude's statement runs. Pause and Stop cancel a running statement.
- **An app that can run commands can approve for itself.** Claude Code can run commands as you. DataCanvas keeps its session link in your data folder (`run.json`, mode 0600) so that a second start finds the running one; a program running as you, including such an app, can read it and call the routes that approve, pause and share. The approval prompt protects against mistakes and against a model that has only the tools DataCanvas offers, **not against an app with a shell**. If that matters, use Claude Desktop without shell tools, or a database user that cannot read what must not leave.
- **A database's error text is not passed on**, because it can hold a value (`invalid input syntax for type integer: "..."` repeats the text of a row, and a query can make it do so for any column). Only our own refusals, time and size limits and errors about names (SQLSTATE class 42) **in which every quoted part is text of the statement itself** are put into words (`relation "<a value of a row>" does not exist` is not); any other is "The database refused the statement (SQLSTATE ...)".
- **A powerful role needs a second yes.** A superuser, or a role that can read server files or run programs, can do outside a read-only transaction what the transaction does not stop. Sharing the data level with one asks you to confirm.
- **Prompt injection.** A value in a table can say anything, and a model may read it as an instruction. Claude has only read tools, and each data call can be approved by you, but a model that is led astray can still ask for rows and the Claude app sends them on. Read what you approve.

## Bulk changes and import (1.9.0)

These need the same three things as any change (`--enable-writes`, a database on this machine, the unlock) and go through the same preview and apply.

- **Bulk change.** Rows are chosen in the grid (kept in your browser's memory only) and a change is **Set a value** or **Delete** on up to 500 of them. It adds no kind of statement: each row is the single-row `UPDATE` or `DELETE`, found by the table's whole key with every value bound, and each must change exactly one row or **the whole transaction is rolled back**. A row that changed since you loaded it (or is gone) is found when you preview, left out and counted, without its values (a delete compares no values: only a row that is gone is left out); one that changes between preview and apply rolls everything back.
- **Import.** A CSV file (UTF-8, or UTF-16 or Windows-1252 from 1.12.0; up to 100,000 rows, 50 columns, 20 MB) is read **in your browser**; the server never parses a file. You choose which table column each file column goes to, and **a name in the file is never used as a name in a statement**. The rows are added in batches of 500 of one fixed statement (`INSERT ... SELECT CAST(...) FROM unnest(...)`) whose names come from the catalog and whose values are bound, in **one transaction: every row is added or none is**. Each batch must add exactly the rows it carries, and closing the dialog or losing the connection stops it and rolls it back. The database can check the whole file first with **Validate**.
- What the server sends back, the history and every error hold counts, names and row numbers, never a value. The preview dialog in your browser does show the values you are about to write, from memory only, and the server keeps the bound values of a preview until it is applied or expires.

## Import modes, changes by filter, cell edits and text values (1.12.0)

These need the same three things as any change (`--enable-writes`, a database on this machine, the unlock) and go through the same preview and apply. **They are not available to Claude or to the command line**: the MCP server has no tool that changes anything, and `datacanvas` has no command that does.

- **New write operations.** `upsert_rows` (update by a key and add the rest) and `update_by_key` (update only) for an import, `update_matching` and `delete_matching` for the rows a filter matches, and `edit_cells` for cells edited in the grid. Like every operation they are strict schemas with no field that holds SQL or a condition, built from names checked against the catalog, with every value bound as a parameter. Two statement shapes are new: the import batch with `ON CONFLICT (key) DO UPDATE` or `DO NOTHING`, and `UPDATE ... FROM unnest(keys, values)` and `DELETE ... USING unnest(keys)` in batches of 500. The key an import matches on is re-derived from the table's own primary key and unique constraints at preview (a request cannot name any other; partial, expression, deferrable and nullable keys are not offered), and every batch must report exactly the rows it carries or the whole transaction rolls back.
- **A filter never becomes a `WHERE` in a write.** For "all matching rows" the filter is used only by the **read of the preview**, which finds the keys of the matching rows (key columns only, in a read-only transaction). The server **holds those keys** in the plan, in memory, for at most five minutes (one such plan per connection, dropped on lock, disconnect or switching data viewing off) and sends back only their count. Apply changes or deletes exactly those keys. An empty filter is refused. At most 100,000 rows and 8 million characters of key text are held (a key value is at most 4,096 characters), so a filter that matches more is refused ("narrow the filter"). The rows are found by their key when you apply: a row deleted and replaced by another with the same key between the preview and the apply is changed, on purpose, because the key is the identity the person sees; a row that was deleted or re-keyed makes a batch short and rolls everything back. This change does not compare the values you saw, and the preview says so.
- **What the preview counts.** An import by key counts, with one read-only join of the file's keys against the table, how many rows exist and how many would be added or overwritten, and says so first; where PostgreSQL cannot say row by row (a partitioned table, or a role that may not read the table) the result's split is the preview's estimate. A change by filter shows the count the keys came to. Neither shows a value.
- **The destructive tick is enforced by your browser.** An import that overwrites rows, an update by key, and a change of the rows a filter matches are marked destructive by the server and need the tick before **Apply** is enabled in the dialog; the server does not check the tick, as for a delete since 1.4.0. For a change by filter the server does check one thing itself: the apply request must carry the count the preview found, typed by the person, and any other number is refused before the preview is used up. Anyone who already holds the session token and has unlocked writes can call apply without the dialog, which is the stance of every write (see the limits below).
- **Cell edits** (`edit_cells`) change up to 500 rows, 50 cells a row and 2,500 cells in all, one `UPDATE` per row with its own columns and its own expected values, each checked to change exactly one row. A row whose cells no longer hold the values you saw is left out and counted at preview (none left is refused); it is not destructive, so it has no tick. Key, hidden, generated and `bytea` columns are refused by the server's planner, not only by the grid.
- **A text value the grid cut short** is read whole by the same read as a JSON value (`getCell`, 1.8.0), now also for `text`, `varchar` and `citext` columns: behind the data-access check, by the row's whole key, with a hidden column refused unless revealed, a value over 1,000,000 characters measured and not sent, and editing allowed only up to 100,000 characters. It writes nothing; a changed value is a pending cell edit like any other.
- **The rejects file** of an import is made in your browser from the file you already hold and saved by your browser; DataCanvas keeps nothing of it, and what the server reports about failing rows is row numbers and rule names, never a value. The file holds the values of the failing rows, so treat it like the original.
- A history entry, an error, a log and `skipped` hold counts, names and positions, never a value or a key.

## Validation, the pre-flight and export

These three read table data, so they need **data viewing** on, like the page of rows.

- **Validate** (the edit and add-row forms) asks whether the database would accept the values, without writing a row. The values go into a temporary copy of the table (its types, NOT NULL, CHECK and generated columns, with no triggers, foreign keys, defaults or indexes) in a transaction that is switched to read-only before the first value goes in and is always rolled back, so a rule of the table that tries to change data fails instead. Uniqueness and foreign keys are asked by read-only queries on the real tables. The answer holds rule names, column and constraint names, counts and row numbers, never a value. It needs the right to create temporary tables, and says what it did not check (triggers, row-level security, partial and expression unique indexes).
- **Check against the data** (Migrations) runs four fixed read-only counts built from names that are looked up in the database's catalog. It does not run the text of a check constraint or try a type conversion: that text can come from a snapshot file.
- **Export** writes the rows you are looking at, with the filter and sort on screen, as a file: up to 100,000 rows and 64 MB, then a line that says it was cut. Columns whose names look sensitive are left out unless you showed them, and the file names them. A value a spreadsheet would run as a formula gets a leading apostrophe. One export runs at a time per connection, and closing the dialog stops the read in the database. The file is made on your machine from rows you could already see, and DataCanvas keeps nothing of it.
- The **JSON editor** reads one `json` or `jsonb` value whole (up to 1 million characters) by its row's key, behind the same check as a page of rows, and writes nothing: a changed value goes through the same preview and apply as any edit.

## Before you export a diagram

A PNG, SVG or workspace file shows **table and column names**. That can reveal how a system works. It contains no row data, whether or not data viewing is on, and is created on your machine, but share it only with people who should see your schema.

The Data section is not exported or saved. If you share your screen, a screenshot or a recording while it is open, rows are visible; the **Blur values** switch hides them on screen, but it is for that purpose only and does not change what is read.

## Known limits

- Another program running as **your user** can read the process list and so the token. DataCanvas does not defend against an attacker who already has your account.
- The token travels over plain `http` on loopback. Other users on a shared machine cannot normally see loopback traffic, but this is not hardened against a hostile administrator.
- Cookies are not isolated by port; other web apps on `127.0.0.1` receive the cookie. The Origin and `Sec-Fetch-Site` checks stop them from using it from a browser.
- The Content-Security-Policy allows inline styles (see above), and `'strict-dynamic'` lets a script that already runs add scripts: markup that the parser reads cannot run, but a script that is already running is trusted.
- Passwords live in memory, so they are present in a memory dump of the process. So are the rows of any page you have open, in the server and in your browser, and they can end up in the operating system's swap.
- Hiding columns by name is a hint, not a control. A column called `notes` can hold a password; one called `token_count` is harmless. Use a database user that cannot read what DataCanvas should not show.
- Browser extensions with access to the page can read what the page shows, including rows.
- Row-level security can silently return fewer rows; the Data section says so only when it applies to your database user.
- A sort or a condition can make the database scan a whole table. Such reads are stopped after 5 seconds, one runs at a time per connection, and the page says so, but each try can still cost the database up to 5 seconds of work. Use a database user with the limits you want.
- A condition's value is held in memory and sent in a request body; like the rows, it is never saved, logged, or put in an error message.
- With writes unlocked, anyone holding the session token can change that local database. Lock writes, or start DataCanvas without `--enable-writes`, when you are done.
- A tunnel or proxy on `127.0.0.1` to a remote database counts as local (see above).
- The SQL tab runs what a role is allowed to run: a function with effects outside the database (through an extension such as `dblink`, or a privileged role) is not stopped by a read-only transaction. A statement can also change its own time limits for the rest of its transaction, which only matters to the few queries we run after it. A pooler such as PgBouncer can make Cancel reach the wrong session; use a direct connection for SQL you may need to cancel.
- A change can wait up to 3 seconds for a lock; once it has the lock, a long `ALTER TABLE` (a type change rewrites the table) blocks every other query on that table until it finishes. The preview says when a change takes such a lock or rewrites the table.
- A file you export is yours: DataCanvas cannot protect it after your browser saved it. A column whose name does not look sensitive can still hold a secret, and an export includes it. Export from a database user that cannot read what must not leave.
- A **validation** reads and writes only a temporary table, but it takes up to 100,000 rows now, and it works on a connection that is not local and without the unlock: on a remote database it writes that much into a temporary table of your session.
- Validation does not run row triggers or check row-level security, but it is not free of side effects: **event triggers** fire when its temporary copy is made, before the read-only switch, so one can write or advance a sequence; and a function in a CHECK that has effects outside the database (through an extension such as `dblink`) is not stopped by a read-only transaction or undone by the rollback. The role you connect with is the control.
- An import or a bulk change fires the table's row-level triggers once for each row (and its statement-level triggers once for each statement: once for each batch of up to 500 rows of an import), and can fill a table with up to 100,000 rows in one transaction (the preview says how many statements and batches). Rows added by an import are not undone by DataCanvas after the transaction commits: try a file in a test copy first when it matters. A file's contents can include values that look like formulas; they stay text in a text column (another column type casts each value, and may refuse it), and a spreadsheet that later exports them is yours to guard.
- Triggers on a table run when you change a row, and can do anything their code does. The preview names them.
- **1.12.0 limits.** The tick of a destructive change is enforced by the browser's dialog, not by the server (the typed count of a change by filter is checked by the server). The held keys of a change by filter use memory (up to about 17 MB of key text for one plan, and one plan per connection). Only PostgreSQL 17 has run the new tests so far; the run on 12 to 16 and 18 is still to do, and some behaviours (what `xmax` reports, the planner's estimates) may differ between versions. Preview of an edit of many different cells is slow (a type check for each distinct value; 25,000 cells took 25 seconds, which is why a change is capped at 2,500).
- A destructive step you leave unconfirmed is written commented out, and so is every later step that needs it or is about the same object, with the reason. Steps that only touch other things still run: confirm or leave out steps together.
- A migration is as good as the structure it was made from. A structure read while another migration runs can mix before and after, and a migration made from an old snapshot may not fit the database it is run on: read it first, and run it in a test copy when you can.
- Two DataCanvas processes sharing one data folder are not coordinated.

The full reasoning is in [docs/threat-model.md](docs/threat-model.md).
