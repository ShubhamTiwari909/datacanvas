# Decision records

Short records of choices that are not obvious from the code. Newest at the bottom. Each entry says what we decided, why, and what we gave up.

## 1. Next.js route handlers instead of a separate backend server

**Decision:** the API is `app/api/**/route.ts` inside one Next.js app. No Fastify or Express.

**Why:** a browser cannot speak the PostgreSQL protocol, so server-side code is required, but Next.js already runs Node. One app means one process and one port, no CORS or proxy, and simpler packaging for `npx`.

**Trade-off:** less built-in structure than Fastify. We keep route handlers thin and put all database logic in framework-free packages (`database-core`, `postgres-adapter`) so a dedicated server stays possible later.

## 2. PostgreSQL only for v1

**Decision:** MongoDB is deferred. The adapter interface in `database-core` stays so other databases can be added later.

**Why:** a focused first release. Avoid abstractions for databases we are not building.

## 3. No native dependencies, no postinstall scripts

**Decision:** nothing that needs compiling or platform-specific binaries (for example `keytar`, `sharp`, `better-sqlite3`, `pg-native`).

**Why:** the end user should only need Node.js and one `npx` command. Native modules fail on some machines and slow the first run.

**Consequence:** no OS-keychain password storage in v1; Next.js image optimization stays disabled.

## 4. Credentials are memory-only; workspaces are files

**Decision:** database passwords live only in server memory for the current run. Connection profiles (without passwords) and workspaces are JSON files in `~/.datacanvas/`.

**Why:** avoids storing secrets on disk. Files are used instead of browser IndexedDB because IndexedDB is tied to the origin including the port; a fallback port would silently hide saved workspaces.

## 5. Fixed default port 4747

**Decision:** try 4747 first, fall back to another free port only if needed.

**Why:** a stable origin between runs keeps behaviour predictable and makes the security checks (Host and Origin validation) simple.

## 6. Monorepo with npm workspaces and TypeScript project references

**Decision:** one repo, npm workspaces (`apps/*`, `packages/*`), and `tsc -b` with project references for the plain TypeScript packages.

**Why:** shared types and database packages are consumed by several workspaces. npm workspaces needs no extra tool; project references give correct build order and incremental builds.

**Note:** the Next.js app (Phase 1) uses its own bundler resolution and overrides the `module` settings from `tsconfig.base.json`.

## 7. Minimum Node version

**Decision:** `engines.node` is `>=20.9.0`.

**Why:** confirmed in Phase 1: Next.js 16.4.6 declares `engines.node >=20.9.0`, so that is our floor. (This is the floor for RUNNING the published package. Building from source needs a newer Node; see decision 107.)

## 8. Package name

**Status:** `datacanvas` returned 404 on the npm registry on 2026-11-12, so it appears to be available. Re-check right before the first publish, since a name can be taken at any time.

## 9. ESLint 9 (not 10)

**Decision:** ESLint is pinned to the 9.x line.

**Why:** `eslint-config-next` pulls in `eslint-plugin-react` and friends, whose declared peer range stops at ESLint 9. Using ESLint 10 produced peer-dependency conflicts. It also cleared the dev-only `minimatch` audit finding that came with ESLint 10's dependency tree. Revisit when the Next.js ESLint plugins support ESLint 10.

## 10. System font stack instead of a web font

**Decision:** the UI uses the operating system's default font (`ui-sans-serif, system-ui, ...`) instead of `next/font/google`.

**Why:** a Google font is downloaded at build time, so offline builds would fail and contributors would need internet access just to build. System fonts need no download and keep the app fully offline. The shadcn CLI generated the Geist font setup; we replaced it.

## 11. shadcn/ui with Radix primitives

**Decision:** shadcn/ui (`radix` base, `neutral` colors) generated into `apps/web/components/ui`.

**Why:** components are copied into the repo (we own and can edit them) rather than imported from a runtime UI library, so there is no extra runtime dependency beyond Radix, `lucide-react` and a few small helpers: `cn` (class-name merging, published by the shadcn maintainer), `class-variance-authority`, `tw-animate-css`, and the `shadcn` package itself, which supplies a CSS file imported by `globals.css`. `npm audit` flags a prototype-pollution advisory in `deepmerge` inside the `shadcn` package; it is used for CSS/CLI tooling, not at request time. Revisit when shadcn publishes a fixed release.

## 12. Runtime dependencies live at the package root and are bundled

**Decision:** the published package puts the Next.js server's `node_modules` at its root and lists every package in both `dependencies` and `bundleDependencies` (generated by `scripts/build-package.mjs`).

**Why:** `npm pack` never includes a nested `node_modules`, and only bundles a package that appears in both fields. This keeps installation download-free and independent of the registry for those packages.

**Trade-off:** the package is larger (about 3.4 MB compressed) and the `dependencies` field is generated, not hand-written.

## 13. Prune `sharp` when packaging

**Decision:** the packaging script deletes `sharp`, `@img`, `@emnapi` and `detect-libc` from the copied `node_modules`, and fails the build if any `.node` file is present.

**Why:** Next.js' standalone tracer copies the native `sharp` module and a binary for the build machine's OS even when `images.unoptimized` is set. It would not run on other platforms and violates the no-native-code rule. `outputFileTracingExcludes` does not reach this shared trace, so pruning is the reliable fix. Safe because `sharp` is only loaded when optimising images, which we never do.

## 14. The CLI is bundled with esbuild

**Decision:** `scripts/build-package.mjs` bundles `packages/cli` into one `bin/datacanvas.mjs` with esbuild (a dev-only dependency).

**Why:** the CLI imports a workspace package that is not published on npm. Bundling inlines it, so the published package has no runtime dependency on any other DataCanvas package, and the CLI starts as a single file.

## 15. Vitest for unit tests from Phase 2

**Decision:** add Vitest now rather than at Phase 12, with tests next to the code (`*.test.ts`).

**Why:** the plan requires every meaningful change to be tested. Route handlers return a standard `Response`, so they are plain functions that tests can call directly, with no server needed. Playwright end-to-end tests still arrive in Phase 12.

## 16. Explicit `--port` is strict, the default port falls back

**Decision:** with no `--port`, the CLI uses 4747 or the next free port; with `--port N` it fails if N is busy.

**Why:** a user who names a port wants exactly that one; silently using another would be surprising. The default is a convenience, so falling back is friendlier than failing.

## 17. Zod schemas are the API contract

**Decision:** request and response shapes are Zod schemas in `@datacanvas/shared-types`; TypeScript types are inferred from them (`z.infer`). Plain interfaces from Phase 2 were replaced.

**Why:** one definition gives runtime validation and the compile-time type, and both the browser and the server use it, so they cannot disagree.

**Trade-off:** Zod ships to the browser (the form validates there too). Accepted for a local app; `sideEffects: false` keeps the CLI from bundling it.

## 18. Default TLS mode is "verify-full"

**Decision:** when no SSL mode is given (field form default, or no `sslmode` in a pasted string), DataCanvas assumes `verify-full`. Only `disable`, `require` and `verify-full` exist; `verify-ca` is treated as `verify-full`; `allow` and `prefer` are rejected with a message.

**Why:** libpq's default `prefer` silently falls back to an unencrypted connection, which is the wrong default for a tool that handles credentials. The cost is that a local database without TLS needs `?sslmode=disable` (or the "disable" option), so the UI should explain this when a connection fails (Phase 6).

## 19. Strict, non-coercing request validation

**Decision:** objects use `z.strictObject` (unknown keys are errors) and numbers are not coerced from strings.

**Why:** the API is internal, so strictness costs nothing and catches client bugs early. Quietly accepting extra or mis-typed fields is how unexpected data reaches the database layer.

## 20. Request hardening in the parsing helper

**Decision:** `parseJsonBody` requires `Content-Type: application/json`, caps the body at 64 KB by streaming, and returns only generic validation messages.

**Why:** the content-type rule blocks plain cross-site HTML form posts (a first, partial CSRF defence; Phase 10 adds Origin and token checks). Streaming the limit handles clients that omit or fake Content-Length. Generic messages avoid echoing secrets.

## 21. A validate-only endpoint exists before Phase 6

**Decision:** `POST /api/connections/validate` parses and normalises connection details without connecting.

**Why:** it lets Phase 3 demonstrate server-side validation end to end (and lets the UI show what was understood) without database code. Phase 6 may keep or replace it.

## 22. `shared-types` uses the DOM `lib` for the `URL` type

**Decision:** its tsconfig includes `lib: ["ES2022", "DOM"]`.

**Why:** `URL` exists at runtime in both Node and browsers but is typed only by the DOM lib. The package must therefore avoid other browser-only APIs; this is noted in its tsconfig.

## 23. Metadata models are plain TypeScript types in `database-core`

**Decision:** `SchemaInfo`, `TableInfo`, `ColumnInfo` and the rest are interfaces, not Zod schemas, and `database-core` has zero dependencies.

**Why:** they describe the domain, and Phase 5 will still adjust them once real catalog queries exist. Plain types are cheap to change and keep the package dependency-free.

**Open question for Phase 6:** the browser will receive these over HTTP and should verify them with Zod, like every other API response. The plan is to define the response schemas in `shared-types` and type-check them against these interfaces (so the two cannot drift), rather than duplicating the models.

## 24. Fine-grained adapter methods, no bulk fetch yet

**Decision:** the interface has one method per kind of detail (`getColumns`, `getConstraints`, `getIndexes`) plus one database-wide `getRelationships()`.

**Why:** simple to implement and test. The trade-off is that drawing a canvas of N tables takes about 3N calls. We will measure in Phase 7 and add a bulk method (for example "details for these tables") only if it is actually slow. Relationships are already one call because the canvas always needs every edge.

## 25. `connect()` and `testConnection()` have separate, precise meanings

**Decision:** `connect()` opens and verifies a connection and is idempotent. `testConnection()` verifies without keeping anything open and works whether or not `connect()` was called.

**Why:** the UI has two distinct buttons (Test, Connect). A self-contained `testConnection()` means the Test flow never leaves a stray connection behind.

## 26. `not_found` and `not_connected` are errors, not empty results

**Decision:** asking for a schema or table that does not exist throws `not_found`; calling a data method on a closed adapter throws `not_connected`.

**Why:** an empty list is ambiguous (a table with no columns versus a table that does not exist), and a clear error gives the UI something specific to say. The real adapter will check existence with a cheap catalog query.

## 27. Registry generic over a config map, backed by a `Map`

**Decision:** `AdapterRegistry<TConfigs extends object>` is typed by a map of provider name to its connection-details type; storage is a `Map`.

**Why:** keeps each provider's config type precise without `database-core` importing any provider or its types. `Map` avoids inherited-property surprises for names like `constructor`. `object` (not `Record<string, unknown>`) so interfaces work as config maps.

## 28. Mock adapter ships as a separate entry point

**Decision:** `@datacanvas/database-core/testing` exports the mock adapter and sample data; the main entry point does not.

**Why:** production code cannot import it by accident, and the intent is visible at every import site. A shared contract test suite (run against both mock and real adapters) is deliberately postponed until Phase 5 gives us a second implementation.

## 29. Architecture rules are tests

**Decision:** `tests/architecture.test.ts` fails if `database-core` gains a dependency or imports anything but relative modules.

**Why:** "no provider-specific dependency leaks into database-core" is a completion criterion; a test keeps it true after we stop watching.

## 30. Each operation runs in a READ ONLY transaction

**Decision:** every adapter call wraps its queries in `BEGIN READ ONLY`, with the statement timeout set through `set_config(..., true)` (transaction-local).

**Why:** the database server then refuses any write, even if our code had a bug. The alternative (startup parameters such as `options=-c default_transaction_read_only=on`) is rejected by connection poolers like PgBouncer, which many real databases sit behind; a per-transaction setting works everywhere and cannot leak onto a reused pooled connection.

## 31. Read `pg_catalog`, not `information_schema`

**Decision:** metadata queries use PostgreSQL's own catalogs.

**Why:** `information_schema` hides objects the current user has no privileges on, omits PostgreSQL-specific things (materialized views, partition details, index access methods, expression indexes) and is slower. The cost is that the SQL is PostgreSQL-specific, and some columns depend on the server version.

**Supported versions:** the queries use `indnkeyatts` and `conparentid` (PostgreSQL 11+). Tested on PostgreSQL 17. Treat 12 or newer as supported (11 is end of life).

## 32. What the explorer shows and hides

**Decision:** system schemas (`pg_*`, `information_schema`) are hidden; individual partitions are hidden while the partitioned parent is shown; foreign tables are not listed yet; only primary key, unique, foreign key and check constraints are reported.

**Why:** a table split into 100 partitions would otherwise bury the one logical table. Foreign tables and exclusion constraints can be added when there is a need.

## 33. Cardinality is derived in TypeScript from unique indexes

**Decision:** `deriveCardinality` takes the foreign key columns and the table's unique keys. Partial, expression and invalid indexes are ignored.

**Why:** pure logic is easy to unit test, and a partial unique index (unique only `WHERE status = 'open'`) must not turn many-to-one into one-to-one.

## 34. Error mapping order: SQLSTATE, then Node codes, then message patterns

**Decision:** `mapPgError` checks exact SQLSTATE codes first, then Node/TLS codes, and only then regular expressions on the message. Unknown errors become `unexpected`.

**Why:** codes are precise and stable; messages vary by version and locale. The message fallback exists because the driver throws plain `Error`s for some failures (connection timeout, TLS not supported). A failure to match is safe, because it only loses detail; it never leaks.

**Changed:** the `ssl_error` message in `database-core` now covers both "server has no TLS" and "server requires a different SSL setting", because a `pg_hba.conf` rejection can mean either.

## 35. Integration tests use a disposable server and a per-run database

**Decision:** tests read `DATACANVAS_TEST_PG_URL`, create `dc_test_<random>` plus a role in that server, run, and drop them. Without the variable they are skipped. `examples/docker-compose.yml` provides a server on loopback port 54329.

**Why:** isolation (nothing pre-existing is touched), no setup for people who only run unit tests, and a non-default port so the test server cannot be mistaken for a developer's own PostgreSQL. The account must be able to create databases and roles, so never point the variable at a server that holds real data.

## 36. One contract suite for every adapter

**Decision:** `@datacanvas/database-core/contract` exports `describeAdapterContract`, run by both the mock and the PostgreSQL adapter. It is a separate entry point because it imports `vitest`.

**Why:** the mock is only trustworthy while it behaves like the real thing. The same assertions on both make drift fail a test. The suite checks the shared shop schema; a real database may contain extra objects.

## 37. Defensive details in the connection code

- `pool.on("error", noop)`: an idle connection dropped by the server is reported as an `error` event; without a listener Node would crash the whole process. The next query surfaces the real failure.
- `testConnection()` uses its own single `pg.Client`, never the pool, so testing cannot change whether the adapter is connected; it only calls `end()` on a client that actually connected (ending a failed one can hang).
- Concurrent `connect()` calls share one attempt, so no duplicate pools are created.
- `ssl` is always set explicitly (see architecture notes).

## 38. Local databases default to no TLS (revises decision 18)

**Decision:** when no SSL mode is given, connections to `localhost`, `127.0.0.1` and `::1` use `disable`; every other host still defaults to `verify-full`. An explicit choice always wins. In the form the SSL field is "Automatic" by default and says which mode that means.

**Why:** pasting a local connection string was the most common first action, and it failed with a TLS error because a typical development database has no TLS. Traffic to this machine never crosses a network, so encryption protects nothing there. Remote hosts keep the strict default. To support this the `fields` schema's `sslMode` became optional and is resolved from the host in `resolvePostgresConnection`.

## 39. Connections live in an in-memory registry; credentials never touch disk

**Decision:** the server keeps `id -> { summary, adapter }` in memory. The adapter holds the password privately. Nothing is written to disk, and everything is gone when DataCanvas stops. `DELETE /api/connections/:id` discards one immediately. Saved connection profiles (without passwords) arrive in Phase 8.

**Why:** the safest place for a secret is nowhere persistent. The cost is re-entering the password after a restart.

**Details:** ids are 128 random bits (`randomBytes(16)`, base64url); at most 10 connections (bounds pools and memory); idle connections close their database sessions after 30 minutes but keep credentials and reconnect on the next request.

## 40. Services take their dependencies through the constructor

**Decision:** `ConnectionService({ adapters, connections })`; route handlers fetch the shared instance from `getServerContext()`, which tests replace with `setServerContextForTests`.

**Why:** the same service runs against mock adapters in unit tests and the real adapter in production, with no module mocking. The context lives on `globalThis` because Next.js dev reloads modules and would otherwise drop every open connection (a consequence: changing server code in dev needs a restart to take effect in already-built services).

## 41. HTTP status mapping for database failures

**Decision:** wrong credentials, database name, TLS setting or privileges are 400 (the request was fine, the details are wrong); unreachable server is 502 and timeout is 504 (we are a gateway to it); missing schema or table is 404; everything unexpected is 500 with a generic message.

**Why:** gives clients a meaningful class of failure without exposing details. We avoid 401 and 403, which would be confused with DataCanvas' own authentication from Phase 10.

## 42. One endpoint for table details; the validate-only endpoint is removed

**Decision:** `GET /api/connections/:id/tables/:table` returns columns, constraints and indexes together, instead of separate `/columns`, `/constraints`, `/indexes`. `POST /api/connections/validate` (Phase 3) is gone because `/test` and `POST /api/connections` validate with the same schema and do more.

**Why:** one click would otherwise cost three requests, and dead endpoints are maintenance. Opening a table still issues three parallel requests (details, table list for the header, relationships); Phase 7 will cache these.

## 43. Metadata schemas are checked against the domain types at compile time

**Decision:** `shared-types/src/metadata.ts` defines Zod schemas for the models; `metadata.test.ts` contains type-level assertions that each schema infers exactly the corresponding `database-core` interface, and that every database error code is a valid API error code. Real mock-adapter output is also parsed with the schemas.

**Why:** answers the open question from decision 23 without duplicating the models: if either side changes alone, `tsc` fails.

## 44. Zustand for shared UI state; the server remains the source of truth

**Decision:** `useWorkspaceStore` holds connection summaries, the selected connection and table, and dialog state. Server data that is purely derived (schemas, tables, details) is loaded with `useAsyncData`, not kept in the store.

**Why:** the sidebar, main panel and dialog all need the same selection, which would otherwise mean prop drilling. Keeping fetched data out of the store avoids a second copy that can go stale.

## 45. Packaging replaces Turbopack's alias symlinks with shim packages

**Decision:** `build-package.mjs` turns `.next/node_modules/pg-<hash>` (a symlink) into a real package `node_modules/pg-<hash>` containing `module.exports = require("pg")`.

**Why:** `npm pack` omits symlinks, so the packed app failed with `ERR_MODULE_NOT_FOUND` for `pg-<hash>`. The failure only appeared when running the packed tarball, which is why packaging is verified that way after every phase that adds server code.

## 46. Known limits left for later phases

- **Graceful shutdown:** on SIGTERM the server process exits and the operating system closes the sockets; connections are not explicitly closed first. Phase 11 handles shutdown properly.
- **Small screens:** the sidebar is hidden below the `md` breakpoint, so on a phone there is no way to pick a table. The canvas in Phase 7 is desktop-oriented anyway.
- **Large schemas:** the tree is not virtualised; thousands of tables in one schema will be slow to render.
- **No request authentication yet:** any local process or web page that can reach 127.0.0.1 can call the API. Phase 10 adds Host/Origin checks and a session token.

## 47. A bulk adapter method, `getTablesDetails` (resolves decision 24)

**Decision:** `DatabaseAdapter.getTablesDetails(tables)` returns the description, columns, constraints and indexes of many tables in one call, in request order, with duplicates collapsed, all-or-nothing (`not_found` if any table is missing). The PostgreSQL implementation always uses four queries. The existing per-table queries were rewritten as the bulk query with a list of one, so each query exists once.

**Why:** decision 24 said to measure first. Per table the old path cost about five round trips in three transactions, which is fine locally but would take tens of seconds for a hundred tables on a remote database. **Trade-off:** the interface grew by one method, which the mock and the contract suite had to implement and test.

**API:** `POST /api/connections/:id/table-details` with 1 to 500 tables. It is a POST although it only reads, because the table list does not fit comfortably in a URL.

## 48. `canvas-engine` holds the canvas logic; React Flow stays in the web app

**Decision:** node sizing, layout, edge building, ids and search live in `packages/canvas-engine` with no React and no canvas library; an architecture test enforces that.

**Why:** the geometry is where the bugs are (overlaps, which handle an edge attaches to), and pure functions are easy to test exhaustively, including with seeded random inputs. It also keeps the option to reuse the logic for exports or another renderer.

## 49. Canvas layout and database metadata are separate stores; edges are derived

**Decision:** the canvas store keeps only what the user arranged; the metadata store caches database structure; edges are computed from both and never stored.

**Why:** a saved workspace (Phase 8) should contain layout, not a copy of the schema that may be out of date; and derived edges cannot get out of sync. The metadata cache is not refreshed automatically: reconnecting shows a changed database.

## 50. Node and handle identifiers

**Decision:** a node id is `tableRefKey` (a JSON array of schema and name). Handle ids are `source:column:<name>` / `target:column:<name>` for rows and `source:table` / `target:table` for the header.

**Why:** joining schema and table with a dot would make `a.b` + `c` collide with `a` + `b.c`. A column literally named "table" cannot clash with the header handle (a test covers it).

## 51. Layout: a grid, then the next free slot

**Decision:** the first tables on an empty canvas are laid out in a `ceil(sqrt(n))` grid (rows as tall as their tallest table); later additions take the first free slot; "Reset layout" re-grids everything in reading order. Layout uses estimated heights.

**Why:** simple, predictable and overlap-free (tests use seeded random heights). Relationship-aware layout and grouping are Phase 9 (ELK.js).

## 52. Wide tables are collapsed to 12 columns, with a header fallback for edges

**Decision:** a collapsed table shows its first 12 columns and a "+ N more columns" footer. An edge whose key column is hidden attaches to the table header instead of being dropped (React Flow would not draw an edge to a missing handle).

## 53. Keyboard, deletion and user-drawn links

- Delete or Backspace removes the selected tables from the canvas only; the database is never touched.
- Tables cannot be connected by hand (`nodesConnectable={false}`): relationships come from the database. User-defined links (the plan's "confirmed versus user-defined" distinction) are not built yet.
- Resizing nodes was skipped: fixed width keeps layout estimates reliable.
- The React Flow attribution is kept visible.

## 54. Known limits of Phase 7

- **No persistence:** the canvas and viewport are lost on reload (Phase 8).
- **Expanding a table does not push its neighbours:** it can overlap the table below until dragged or "Reset layout".
- **Edges are plain curves** that can pass behind other tables; better routing and layouts come in Phase 9.
- **Accessibility:** buttons and inputs are labelled, but dragging and edge navigation are mouse-oriented.
- **Measured performance** (packed app, 120 tables and 136 foreign keys, all visible): adding the whole schema took well under 2 s including the request; a zoom sweep averaged 18.6 ms per frame (p95 43 ms, worst 79 ms) in the in-app browser. Real hardware and larger schemas were not measured.

## 55. Data lives in `~/.datacanvas`, as owner-only JSON files

**Decision:** `connections.json` plus `workspaces/<id>.json`, in the user's home folder (override with `DATACANVAS_HOME`). Folders are created mode 0700 and files 0600 (no effect on Windows).

**Why:** works regardless of port or browser, is human-readable, and a person can back it up or delete it. Table names can be sensitive, so owner-only permissions are the sensible default. Tests and manual runs use temporary folders; a test suite run leaves the real folder untouched (verified).

## 56. Atomic writes through a temporary file and rename

**Decision:** all writes go to a temporary file in the same folder, are flushed, and are then renamed over the target. Read-modify-write sequences on one file are serialised by an in-process mutex.

**Why:** a crash, full disk or power loss must never leave a half-written file. **Limits:** the folder itself is not fsynced (a power cut right after a save could still lose that one rename), and the mutex only protects against other requests in the same process, which is all that runs (DataCanvas is one local server).

## 57. Two versioned file formats with a migration chain

**Decision:** every file has `format` and `schemaVersion`; upgrades run as `migrations[n]` (n to n+1) before validation; newer versions are refused. Unknown keys inside the current version are stripped, not rejected.

**Why:** old files keep opening after upgrades, and the rest of the code sees one layout. Refusing newer files means an older release cannot read a file, drop the fields it does not know, and save it back, silently destroying data. **Trade-off:** stripping unknown keys inside one version means they would be lost if an older patch release re-saved the file; because layout changes bump the version, that should not occur in practice.

## 58. A workspace stores layout only

**Decision:** tables, positions, expanded flags and viewport; never credentials, column metadata or selection.

**Why:** metadata in a saved file goes stale and doubles the file; credentials must never be on disk; selection is moment-to-moment. A table name plus position is enough to rebuild the canvas from the live database.

## 59. Connection profiles are opt-out, never contain a password

**Decision:** a "Save this connection for next time" checkbox (checked by default) stores host, port, database, user and SSL mode. Reconnecting asks only for the password. The same database is saved once (matching provider, host, port, database and user). Forgetting a profile deletes its workspaces and unlinks any live connection opened from it.

**Why:** local-only, non-secret data, and it is what makes "reopen and find my layout" possible. Defaulting to saved is a privacy trade-off: a user who prefers nothing on disk unticks it, and the host, database and user name are the only things written.

## 60. Layouts are tied to saved connections

**Decision:** autosave only runs for a connection linked to a profile. Others show "This layout is not saved" with a "Save connection" button, which also saves the layout already on screen.

**Why:** a file needs something stable to be found by after a restart; a live connection id changes on every run.

## 61. Autosave design

**Decision:** 800 ms debounce after the last change; skip when the saved document would be identical (signature comparison, positions rounded to 0.1, zoom to 0.001); one save in flight per connection with a follow-up if needed; flush before switching, creating or exporting.

**Why:** dragging fires many events a second, and selection or measurement changes must not touch the disk. **Limit:** after a failed save (for example a full disk) the status shows the error and the next change tries again; there is no background retry loop.

## 62. Stale tables are flagged, not dropped

**Decision:** restoring lists each referenced schema once; tables that no longer exist stay on the canvas as "no longer exists" cards and are saved again with the layout.

**Why:** a temporary difference (pointing the layout at a staging database, a table being renamed) must not destroy the user's arrangement. One listing per schema is far cheaper than one request per table.

## 63. Import never overwrites; export is a plain GET

**Decision:** an import is upgraded, validated, and saved as a NEW workspace attached to the chosen saved connection. An export drops the machine-specific `profileId`, keeps a display-only hint (connection name and database), and uses a header-safe file name (printable ASCII only, no quotes).

**Why:** importing an untrusted file must not be able to replace existing work or inject headers. **Note:** the export is a GET that returns table names; until Phase 10 adds request authentication it is protected only by the loopback binding.

## 64. Corrupt or foreign files

**Decision:** damaged workspace files are skipped (and left in place); a damaged `connections.json` is moved aside as `connections.damaged-<time>.json` and a fresh one is started; a file from a newer release is refused and left untouched.

**Why:** a corrupt file must neither block the feature forever nor be silently deleted.

## 65. Known limits of Phase 8

- Two DataCanvas processes sharing one data folder are not coordinated.
- A deleted workspace cannot be undone.
- Several workspaces may share a name.
- The browser decides where an exported file is saved.
- There is no setting for a custom data folder in the UI (use `DATACANVAS_HOME`).
- Reconnecting a saved connection after a restart always needs the password.

## 66. A small graph module with breadth-first search

**Decision:** relationship questions (what is within N hops, shortest path, clusters) are answered by one pure module, `canvas-engine/src/graph.ts`, using breadth-first search.

**Why:** focus mode, "add related tables" and grouped layout all need the same traversal. Breadth-first search finds the nearest tables first, so a hop limit is exact, and the code is easy to test without a browser.

## 67. Focus and filter state is not saved

**Decision:** filters and focus settings live in `canvas-view-store` per connection and are not written to workspace files.

**Why:** they are temporary ways of looking at the diagram, not part of the arrangement. Saving them would change the file format (and its migrations) for little benefit.

## 68. Server-side search is an adapter method with hard limits

**Decision:** `searchObjects(query, limit)` is on the adapter interface. Queries are 1-100 characters, results are capped at 50 tables plus 50 columns, matching is case-insensitive substring, wildcards are literal, and ranking is exact, prefix, then other.

**Why:** large schemas cannot be searched by loading everything into the browser. Parameterized queries and the caps keep a hostile or careless query cheap and safe; the contract tests make every adapter behave the same.

## 69. ELK for automatic layout, and a license to confirm

**Decision:** use `elkjs` (pure JavaScript, no native code), loaded only when a layout is requested.

**Why:** it gives good layered and packed layouts with no installation steps. **Flag:** its license is EPL-2.0 OR GPL-3.0-or-later; confirm with the relevant internal team before publishing the package. The repository also has no LICENSE file yet.

## 70. Export privacy notice

**Decision:** the export dialog always states that the image contains table and column names, no row data, and is created locally.

**Why:** a diagram of a schema can reveal how a system works; the user should decide consciously who receives it.

## 71. Known limits of Phase 9

- Focus and filters reset when DataCanvas restarts.
- "Add related" adds at most 60 tables per click.
- Export is limited to a maximum image side length; very large diagrams are scaled down.
- Layouts use table sizes at the moment of the request; they are not live.

## 72. One guard module, two enforcement points

**Decision:** the Host, Origin, `Sec-Fetch-Site` and token rules live in one pure module and are applied in `proxy.ts` AND inside every route through `handleRoute`.

**Why:** a security control that exists in one place fails completely when that place is bypassed (a changed matcher, a framework upgrade). Sharing the code keeps the two from drifting; a rule test fails if a route skips the guard.

## 73. Token in the first URL, cookie afterwards

**Decision:** the CLI prints `http://127.0.0.1:<port>/?token=<random>`. The proxy trades it for an `HttpOnly`, `SameSite=Strict` cookie and redirects the token away. The cookie name includes the port.

**Why:** a cookie cannot be read by page scripts or sent by other sites, and the token leaves the address bar (history, screenshots, Referer). Cookies are shared between ports, so two running instances need different names. **Trade-off:** the link in the terminal is a secret while the process runs.

## 74. Missing Origin is allowed; wrong Origin is not

**Decision:** a state-changing request with an `Origin` that is not ours is refused; one with no `Origin` is judged by the token alone.

**Why:** browsers always send `Origin` on cross-site writes, so its absence means a non-browser client, which the token controls. Requiring `Origin` would break harmless tools without adding protection.

## 75. Fail closed in production

**Decision:** `NODE_ENV=production` with no configured token answers every request (except health) with 503.

**Why:** the dangerous failure is a server that silently runs open because an environment variable was lost.

## 76. Audit scope: shipped dependencies

**Decision:** `shadcn` (a component generator used at build time) moved to `devDependencies`; CI runs `npm audit --omit=dev` and fails on moderate or higher.

**Why:** the audit should describe what users actually receive. Before the move, six advisories came only from `shadcn`'s tool chain, none of which is in the published package (checked in `.package/node_modules`). Build-time tools are reviewed separately.

## 77. Known limits of Phase 10

- No full Content-Security-Policy (needs per-request nonces with Next.js).
- A same-user attacker can read the token.
- Other web apps on `127.0.0.1` receive the cookie (blocked from using it in a browser).
- Passwords are in process memory while a connection is open.
- No independent security review.

## 78. Instance reuse through a private run file

**Decision:** the running instance writes `run.json` (pid, port, token, version; mode 0600) in the data folder; a second launch opens that instance's link instead of starting another server. The file is deleted on clean shutdown and ignored when stale.

**Why:** Phase 10's per-run token means the second launch could not otherwise get into the first one. **Trade-off:** the token is also on disk while DataCanvas runs; anyone who can read that file as the same user could already read the server's process environment, so the exposure is the same class (see docs/threat-model.md).

## 79. The app closes its own database sessions

**Decision:** the CLI sets `NEXT_MANUAL_SIG_HANDLE=1`; the server's `instrumentation.ts` handles SIGINT/SIGTERM by disposing the connection registry (3 s limit), then exits.

**Why:** the plan asks for pools to be closed before exit, and credentials should leave memory on purpose, not by accident. The time limit means a hung database can never keep the server alive.

## 80. Test the tarball, not the repository

**Decision:** `scripts/verify-package.mjs` packs, installs into an empty project and drives the installed command.

**Why:** a missing bundled file or a dependency that only resolves inside the repo would pass every monorepo test and fail for the first user.

## 81. Known limits of Phase 11

- Verified on macOS only; Windows and Linux are Phase 12 work.
- `--port` differing from the running instance starts a second server and overwrites `run.json`; only the newest is reusable.
- Simultaneous first launches can race.
- Killing the CLI with SIGKILL leaves the server process behind.
- Tarball size 4.9 MB packed / 22.6 MB unpacked; cold start about 360 ms on the test machine.

## 82. End-to-end tests run against the packaged app

**Decision:** Playwright starts `.package/bin/datacanvas.mjs`, not the dev server, and one throwaway database per test.

**Why:** the dev server differs from what users run (no proxy token flow, different bundling). Testing the assembled package catches packaging mistakes the unit tests cannot.

## 83. Playwright pinned to 1.64.0

**Decision:** `@playwright/test` is pinned to 1.64.0 and only Chromium is tested.

**Why:** 1.64 uses a Chromium build that was already installed on the development machine; a newer release would have needed a large browser download. CI installs its own browser. Firefox and WebKit are left out for now.

## 84. Performance budgets catch changes in kind

**Decision:** the 600-table database test and the 400-table browser test use budgets many times the measured values (database calls 5-25 ms against a 500-1000 ms budget; layout 51-107 ms against 15 s).

**Why:** shared CI machines are noisy. A budget that flaps teaches people to ignore it; one that only trips on a real regression stays useful.

## 85. Known limits of Phase 12

- The CI workflow is unproven until it runs on GitHub; Windows is the likeliest to need fixes.
- Windows cannot be asked to stop gracefully by a script, so the clean-shutdown checks run on macOS and Linux only.
- No tests on other PostgreSQL versions than the one used here (a PostgreSQL 17 service is configured for CI).
- The TLS-mismatch test accepts either `ssl_error` or `unreachable`, because which one PostgreSQL's reply produces depends on the server.

## 86. The release gate reports; it never decides

**Decision:** `npm run release:check` fails while the version, license, repository or security contact are missing, and the package build copies such metadata from the root `package.json` instead of defaulting it.

**Why:** a license and a repository address are legal and organizational decisions. A default would either be wrong or hide that a decision is pending. A failing gate makes the open items impossible to forget, and the release workflow runs it so a tag cannot publish around it.

## 87. Trusted publishing, no stored npm token

**Decision:** the release workflow uses GitHub's OIDC identity (`id-token: write`) and `npm publish --provenance`; no npm token is kept as a secret.

**Why:** a stolen long-lived token can publish malicious versions. Provenance lets users verify which workflow built the package. **Trade-off:** the maintainer must configure the trust on npmjs.com first, and the very first publish of a new package may differ; the checklist says so.

## 88. Screenshots are generated, not hand-made

**Decision:** README images come from a Playwright spec against the sample database (`npm run screenshots`).

**Why:** they stay accurate when the interface changes, contain no real schema, and anyone can regenerate them.

## 89. Known limits of Phase 13

- Nothing is published; no remote exists.
- No demo GIF.
- The license is a draft until the internal team confirms it.
- The CI and release workflows are untested on GitHub.

## 90. Apache-2.0 as the draft license

**Decision:** the project is drafted under the Apache License 2.0 (`LICENSE` is the unmodified official text, verified by its SHA-1 against the known value; `"license": "Apache-2.0"` in the root `package.json`). **This is a draft until the relevant internal team confirms it.**

**Why:** it is permissive like MIT, so it does not obstruct use of a tool, but it adds an explicit patent grant and a contribution clause, which suits a company-backed project. Almost every dependency is MIT, ISC, BSD or Apache-2.0, so they raise no conflict. The exception is `elkjs` (EPL-2.0 OR GPL-3.0-or-later): see decision 69. If it cannot ship, auto-layout can move to a permissively licensed library behind the same `autoLayout` function.

Follow-up decisions are 91 and 92.

## 91. `elkjs` is used under its EPL-2.0 option

**Decision:** `elkjs` is dual-licensed (EPL-2.0 OR GPL-3.0-or-later); DataCanvas uses it under **EPL-2.0**, for now. `scripts/generate-notices.mjs` records that choice in `THIRD-PARTY-NOTICES.md`, with the source address.

**Why:** EPL-2.0 is weak copyleft: it applies to `elkjs` itself (changes to it must be shared under EPL) but not to DataCanvas. The GPL option would reach the whole package. **Still to confirm** with the relevant internal team that organization policy allows an EPL-2.0 dependency. **Fallback:** replace it behind `autoLayout` with a permissive library.

## 92. Ownership and contributions

**Decision:** the repository will live under the organization's GitHub, so `NOTICE` names **AnywhereWorks** as the copyright holder (an assumption taken from the organization, easy to change). No CLA or DCO: contributions rely on Apache-2.0 section 5 (`CONTRIBUTING.md` says so).

**Why:** the maintainer stated that organization ownership is not an issue and that no contributor agreement is wanted. **Revisit** if outside contributions grow or the license changes.

## 93. Foreign tables are listed as their own kind (was a known gap)

**Decision:** `pg_class` entries with `relkind = 'f'` (foreign tables, such as `postgres_fdw` or Supabase wrapper tables) are listed with kind `foreign_table`. They are read like tables (columns, comments, details), shown with their own icon and the label "Foreign table", counted separately in the overview, and left out of the health checks and the path finder (their keys and indexes live on the remote side, and PostgreSQL does not allow foreign keys on them).

**Why:** the first robustness round (`odd-schema` tests) confirmed that these tables were silently hidden, which is wrong for anyone whose data sits behind a foreign data wrapper. **Row estimates:** a foreign table that was never analysed reports 0 (or -1), which cannot be told from "really empty", so a zero estimate for a foreign table is shown as unknown. **History:** this entry first recorded the gap; the odd-schema test that pinned the old behaviour now pins the new one. **Not covered:** nothing is read from the remote side (no rows, no remote catalogs), and foreign tables defined through wrappers other than `postgres_fdw` were not tried.

## 94. PostgreSQL 12 to 18 matrix

**Decision:** the database-facing tests run against PostgreSQL 12 through 18, locally through Docker (`npm run test:pg-matrix`, alpine images) and in CI as a job matrix.

**Why:** catalog layouts and defaults change between versions (`reltuples` is -1 for never-analysed tables from 14, partition behaviour, generated columns from 12). 12 is the floor because the fixtures use generated columns. Older versions are not tested and not promised.

**Status (verified locally, macOS, Docker, 2026-11-13):** the adapter, odd-schema, performance and service tests all pass on 12.22, 13.23, 14.25, 15.20, 16.16, 17.12 and 18.7 (177 tests each). The first run found one problem, in the TEST helper not the adapter: `DROP DATABASE ... WITH (FORCE)` needs PostgreSQL 13, so teardown failed on 12. It now terminates connections and drops, which works everywhere. Managed services (RDS, Supabase, Neon) are still untested.

## 95. The overview reuses existing reads and adds no endpoint

**Decision:** the schema overview is computed in the browser from the schema list, the per-schema table lists and the foreign keys the canvas already loads.

**Why:** a new endpoint would add attack surface and a new contract to maintain for numbers that are cheap to derive. **Limits:** one request per schema (a database with hundreds of schemas makes hundreds of small requests); row counts are the planner's estimates and show "unknown" for never-analysed tables; "no declared relationships" says nothing about databases that use no foreign keys (the page says so when there are none at all). Not covered: tables without a primary key, unused indexes or other health checks, which need the details of every table (a possible next feature).

## 96. Health checks are hints with suggested SQL shown, never run

**Decision:** the Health tab reports structural findings with the reason and a fix, and offers SQL as text to copy. A `DROP INDEX` is suggested only for a plain non-unique, non-primary index; duplicates of constraint-backed indexes get no statement. A missing foreign-key index on a table under 1000 estimated rows is a note, not a warning.

**Why:** DataCanvas has no way to run SQL (decision: no arbitrary-SQL endpoint), and only the owner knows whether an optional relationship or a small table is intended. **Not covered:** unused indexes (needs usage statistics), type mismatches, naming conventions, undeclared relationships guessed from column names, partitions on their own, and anything beyond the first 2000 tables.

## 97. Whole-schema add allows 1000 tables (was 200)

**Decision:** `MAX_TABLES_ADDED_AT_ONCE` is 1000, below the 2000 nodes a saved workspace may hold.

**Why:** the maintainer hit the 200 limit on a real 332-table schema. Measured in a real browser with 1000 tables: adding about 1.7 s, 20 nodes in the page at a time (only visible ones are drawn), the layout algorithm 0.2 to 0.65 s but page work around it in bursts of up to about 0.8 s. **Correction:** the earlier 400-table browser test passed while only 200 tables were on the canvas (its text match was too loose); it now requires the exact count. **Limit:** more than 1000 tables in one schema still adds the first 1000 and says so.

## 98. The path finder follows declared keys only and shows SQL it never runs

**Decision:** routes are built from real foreign keys, in both directions; the join is text to copy (`INNER JOIN`, `SELECT *`, `LIMIT 100`, tables aliased t1, t2, ...). Equally short routes are all shown, up to five.

**Why:** a join does not care which table holds the key, so both directions are followed, but the direction is kept because parent-to-child steps multiply rows. Aliases are numbered because a table called `user` or `order` would need quoting as an alias. No route means no declared chain: joinable columns without a constraint are not guessed (the same promise as the canvas). **Not covered:** `LEFT JOIN` variants, choosing which columns to select, non-shortest routes, routes through views, and joins through tables on a different connection.

## 99. Version 1.0.0, and what was removed for it

**Decision:** the first stable version is 1.0.0 (`packages/cli/package.json`), published to the `latest` tag; `1.0.0-rc.1` was the release candidate under `next`. Before it, code and files that nothing used were removed: `shortestPath` in canvas-engine (the Paths tab has its own search that returns every shortest route), `describeDatabaseError` in database-core (route handlers use `handleRoute`; its documentation had it wrong), an unused screenshot, and the "Phase N" wording in comments and package descriptions. The development plan moved from the repository root to `docs/development-plan.md`, and the release checklist became `docs/releasing.md`.

**Why:** dead code that still has tests looks supported, and two shortest-path implementations invite drift. **How it was found:** a scan for dependencies and exported functions that nothing but their own file or tests refers to found only those two functions and no unused dependency. **Kept on purpose:** `setServerContextForTests` (a test hook that tests need) and exported types used for API completeness.

## 100. Theme: a class on <html>, an inline script, and the choice kept in the browser only

**Decision:** light, dark and system are a `dark` class on `<html>`; the saved choice lives in `localStorage` (`datacanvas-theme`) and is applied by a small inline script before the first paint; "system" follows `prefers-color-scheme` live. Version 1.0.1.

**Why:** a class matches the existing shadcn palette and Tailwind's `dark:` variant; without the inline script a dark-mode user would see a white flash on every load. The script is a fixed constant with no user input; it is the one inline script in the app (the Content-Security-Policy that was listed as a known gap would need a nonce or hash for it). Nothing about the theme is sent to the server or saved in a workspace file. **Not covered:** a high-contrast theme, per-workspace themes, and a color picker.

## 101. Accept ?host= and ?port=; explain sockets instead of supporting them

**Decision:** `?host=` and `?port=` are read when the address has none; a socket path is refused with an explanation; two different hosts or ports are an error. Version 1.0.2.

**Why:** a Cloud SQL string pasted from a Cloud Run configuration failed with a message about URL-encoding that was wrong. Unix sockets cannot be supported usefully: they exist only on the machine running the database or its proxy, and DataCanvas connects over the network, so the message points at the two ways that do work (the instance's address, or the Cloud SQL Auth Proxy on 127.0.0.1). Silent preference between two conflicting hosts could connect to the wrong server, so it is an error. **Not covered:** a CA file for providers with their own certificate authority, tunnels, and fetching IAM tokens.

## 102. Snapshots are structure only, compared in the browser, matched by name

**Decision:** a snapshot stores the structure DataCanvas already reads (schemas, tables, columns, constraints, indexes, foreign keys), sorted, with no row estimates and no rows. The server takes it; the browser compares (`diffStructures` is pure). Items are matched by name, with no rename detection. Snapshots live in `~/.datacanvas/snapshots/`, at most 100, and files can be exported and imported.

**Why:** estimates change with every vacuum, so including them would report drift in a database nobody changed. Taking the snapshot on the server means a file cannot claim to be a structure the server never read, and keeps the "browser sends no structure" rule that workspaces already follow. A pure diff needs no endpoint and works for any two sides, including two different databases. Guessing renames from similar columns would report a guess as a fact. **Deliberately not done:** guessed relationships from column names, and row samples. Both would break promises the docs make today (only declared foreign keys; no row is ever read) and each needs its own decision. **Not covered:** unused-index statistics. (Views, types, sequences, functions, triggers, extensions and policies were added right after; see decision 103.)

## 103. Objects are definitions only, extension members are left out, and "not recorded" is not "none"

**Decision:** one new adapter call, `getObjects()`, returns views (query and what they read), types, sequences, functions and procedures, triggers, extensions and row-level-security policies. Objects that belong to an extension, and functions the server created as part of another object, are skipped. Snapshots store them in a new file format version (2); a version 1 file upgrades with `objects: null`, and a comparison involving `null` skips the objects and says so.

**Why:** extension members would bury the user's own functions (PostGIS alone has several thousand). A range type's constructors were found listed as user functions by the first real run, so internal dependents are skipped too, while identity-column sequences, which carry the same dependency type, are kept (a test pins both). Sequence numbers are text because a bigint limit does not fit a JavaScript number, and the current value is never read because it is data. An old snapshot has no objects; treating that as "none" would report every function as new, which would be a false alarm on every comparison with a pre-existing snapshot. Function bodies and policy expressions are code and rules, not rows, so they do not break the "no rows are read" promise, but they can describe business logic: the docs say a snapshot file should be treated like the schema itself. **Not covered:** see the end of the "Database objects" section of the architecture notes. **Deliberately still not done:** guessed relationships and row samples (each breaks a promise and needs its own decision).

## 104. Unused indexes: read the counters, doubt them, and never advise dropping a constraint's index

**Decision:** one new adapter call, `getIndexUsage()`, reads index scan counters, sizes, whether a constraint owns each index, the last statistics reset and the standby flag. The unused-index check is a warning only for an index of at least 10 MB with counters at least a week old (or of unknown age); everything else is information. It never lists primary key, unique, exclusion, unique-index or invalid indexes, and offers no `DROP` for the only index serving a foreign key.

**Why:** "never scanned" is evidence, not proof. The counters are per server (an index used on the primary reads zero on a replica), start over on a reset, and cannot know about a yearly report. So the screen states the start date, the standby case and the limits, and the severity follows how much evidence there is. A unique index enforces a rule even if no query reads it, and a constraint's index cannot be dropped at all (the exclusion-constraint case was checked against a real server). Statistics counters are not table data, so the "no rows are read" promise stands. **Not covered:** combining counters from several servers, and index bloat.

## 105. Type and naming checks judge only what is unambiguous or relative

**Decision:** foreign key type mismatches are judged for built-in types only; naming checks compare with the database's own dominant style and say nothing when there is none (at least 80% of names, and a minimum number of names).

**Why:** a domain over integer next to an integer looks like a mismatch and is not one, and a wrong warning teaches people to ignore the tab, so unknown types are skipped. A fixed naming rule would flag every table of a database that deliberately uses capitals (common with some ORMs); relative checks flag only the odd one out. **Not covered:** plural against singular, index and constraint names.

## 106. Changes found in review of the first pull request

**Decisions:** (1) Cut definition text carries a fingerprint of the whole text, so a change after the 20,000-character cut is still reported; it is a hash inside the stored text, not a new field, so the file format did not change. (2) The snapshot limit check and the write are one locked step. (3) Triggers and policies that belong to an extension are skipped like the other members; the tests record the membership the way an extension's install script does, because ordinary DDL cannot add them. (4) An unused index on a standby is information only. (5) Unknown counter age still allows a warning for a large index, because most databases never reset their statistics and "unknown" is the usual case; this is stated in the documentation instead of being treated as too young, which would have made the check almost never warn. (6) The snapshot screen, export and docs say "no connection credentials" and that definitions can contain secrets. **Not done:** one-transaction snapshot reads and scanning definitions for secret-looking text (both noted as limits).

## 107. Running the package needs Node 20.9; building it needs Node 20.19 or 22.12

**Decision:** the published package keeps `engines.node >=20.9.0`. The repository's own `engines` is `^20.19.0 || >=22.12.0`, and the CI job `install-qa` builds on Node 22 and then runs the packed package on the Node version under test (20.9.0 and 22).

**Why:** the `install-qa` jobs on Node 20.9.0 failed on every push, including on `main`, because `@tailwindcss/node` loads `magic-string` (ES module only since its 1.x line) with `require()`, which Node supports by default only from 20.19 and 22.12; the error is `ERR_REQUIRE_ESM` inside the PostCSS step of `next build`. The job exists to prove that users can install and run the prebuilt package on the oldest supported Node, and users never build, so building on 20.9.0 tested nothing a user does. **Trade-off:** contributors on Node 20.9 to 20.18 (and on Node 21) can no longer build from source; they get an `engines` warning and a failed build, and must upgrade Node. Users of the published package are unaffected. **How it was found:** reproduced locally by clearing `apps/web/.next` and building on Node 20.13.1 (the same error), and checked that `npm run verify:package` passes on Node 20.13.1 against a package built by Node 22 (22 checks). **A trap:** Next's persistent cache can store the failed PostCSS result, so a build on Node 22 right after a failed build on Node 20 fails too until `.next` is deleted; and a warm cache hides the failure entirely, which is why it passed locally for so long. **Not covered:** running the packed package on exactly 20.9.0 was not possible locally (only 20.13.1 was available); the CI matrix does that.

## 108. Viewing table rows is opt-in per connection, off by default, and remembered with the saved connection

**Decision:** `dataAccess` is a setting of the connection (not part of what is sent to the database). Off for every new connection and for every profile saved before it existed (the connections file moves to version 2 with a migration that turns it off); the person switches it on in the connect dialog, in the sidebar or in a table's Data section; a badge shows when it is on. It is saved in the profile as a non-secret flag. A version 2 file that lacks the flag is refused, not assumed. The profile is written before the in-memory setting, so a disk failure leaves both unchanged. The refusal is checked before anything about the table is looked up, so it answers the same for a table that exists and one that does not.

**Why:** it matches how the other non-secret settings behave, and reconnecting already asks for the password. The project's pitch is "safe to point at anything", so the feature must be visible, off until asked for, and honest in the documents. **Left over:** anyone holding the session token can switch it on (same trust as before, higher stakes). **Full reasoning:** `docs/data-viewer-plan.md`.

## 109. Masking of sensitive-looking columns happens on the server

**Decision:** a column whose name looks sensitive (`password`, `token`, `secret`, `api_key`, `salt` and similar, matched after removing separators and case) is not selected at all. The server returns a marker, and the value never leaves the database. The person can reveal one column for the current view, which reads the page again with that column named; the choice lives in the browser's memory only.

**Why:** hiding a value in the browser would mean the secret had already crossed to it, and made the default meaningless. **Not a security control:** names are only a hint (a column called `notes` can hold a password), and the documents say so in those words. A hidden column cannot be used to sort or filter (decided in `docs/data-sort-filter-plan.md`), because a filter would read it back letter by letter.

## 110. Limits of one read of rows

**Decision:** 50 rows per page by default (25, 50, 100 or 200), the first 100 columns, 200 characters shown in the grid and 2,000 fetched (a cell opens in a dialog), about 2 MB per response (a page is shortened and says so, and always keeps one row), the existing 15 second statement timeout, and one read at a time per connection (three more wait, then `429 rows_busy`). Rows are read by keyset paging on the primary key or a safe unique index; a table without one is paged by position and only to its first 10,000 rows; a materialized view is always read that way.

**Why:** every limit stops one request from becoming an expensive scan or a huge response. No count is ever run (a count scans the table): the size shown is the planner's estimate. Values are cast to text and cut inside the database, so a very large value never travels. **Found by the tests:** a paging cursor built from a displayed (cut) value pages wrongly, so the key is selected a second time untruncated.

## 111. Foreign tables are not read

**Decision:** `getRows` refuses a foreign table with `not_supported`, and the screen says why.

**Why:** a read goes to another server, can be slow, and uses credentials DataCanvas knows nothing about. Revisit later with a warning, if at all.

## 112. Views and materialized views can be read

**Decision:** allowed, including partitioned parents. A view can be slow; the timeout and the one-read rule protect the database.

**Why:** people want to look at a view as much as at a table, and nothing about reading one is different in kind.

## 113. Sort and filter were left out of the first release

_(Shipped in 1.3.0: see decisions 116 to 122.)_

**Decision:** the first release reads rows in key order only. Sorting and filtering are designed in their own document (`docs/data-sort-filter-plan.md`, all decisions settled) and ship later (planned as 1.3.0).

**Why:** they let the browser's choice of column and value shape the `SELECT`, need composite keyset paging, and can cause scans; they deserve their own review of the rules that keep "no text typed by the user becomes SQL" true.

## 114. No export of rows

**Decision:** there is no way to export rows; copying one cell's value is allowed. Rows are never in a diagram, workspace, snapshot or file, and a test fails if snapshot code calls `getRows`.

**Why:** an export would turn a viewer into a data extraction tool and put rows on disk, which the privacy rules rule out.

## 115. Version 1.2.0, and the wording of the changed promises

**Decision:** the viewer is a new feature that changes a documented promise (by default only metadata is read; with data viewing on, rows too), so it is a minor version. The product-wide texts (README, SECURITY.md, the threat model, the guide, the connect dialog, the issue template) change in the same release; statements about one tab become "this tab reads no table rows". A rule test fails if a product-wide document says rows are never read.

**Why:** a promise that is no longer true must not ship in the package, and a promise about one tab must not read as a claim about the whole product. **Order:** 1.2.0 is published first; sort and filter follow as 1.3.0 and editing (`docs/data-editing-plan.md`) as 1.4.0, so each release is small and the wording settles before it grows.

## 116. Sorting and filtering are structured choices, not text: one sort column, up to three conditions, a fixed list of operators

**Decision:** a read can be sorted by one column (the table's key breaks ties) and narrowed by up to three conditions, all required, each a column, an operator from a fixed list (`eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `contains`, `starts_with`, `is_null`, `is_not_null`) and a value of at most 200 characters. The request, the sort and each condition are strict objects, the operator is an enum, column names come from the catalog and are quoted, and every value is a bound parameter. Sort was built before filters so it could ship alone if the filters took much longer; they shipped together, in 1.3.0.

**Why:** "no text typed by the user becomes SQL" is the promise that keeps the viewer safe to point at anything. A sort and conditions let the browser's choice shape the statement, so the statement became a small written family of shapes, and a generated test of 400 hostile requests (names such as `"; DROP TABLE users; --`, `$1`, emoji and 63-byte names) checks it. **Not done:** several sort columns, OR groups, regular expressions, JSON paths, saved filters, a count of the matches (it would scan the table). **Full reasoning:** `docs/data-sort-filter-plan.md`.

## 117. A read with a sort or a condition has a shorter time limit, not a cost estimate

**Decision:** these reads run under a 5 second statement timeout (the adapter's own if smaller); a plain page keeps the usual limit. A read the limit stops is `422 too_slow` with a fixed sentence.

**Why:** measured on 5 million rows (965 MB): indexed reads about 1 ms, an unindexed sort about 230 ms, `contains` on a wide text column nearly 4 seconds. The planner's estimate cannot be trusted to refuse a read: for a filter that matches nothing it estimated a cost of 9 for a read that scanned the whole table, because it assumes the `LIMIT` is reached early. Time measures reality, needs no catalog rules and reuses the existing one-read-at-a-time limit. **Left over:** each try can cost up to 5 seconds of the database's work.

## 118. No "try anyway" button after a read is stopped

**Decision:** a stopped read says why and offers to remove the filters or the sort; there is no override.

**Why:** the 15 second limit already exists for every other read, and an override invites repeated heavy reads against a database the person may not own.

## 119. A table without a key can be filtered but not sorted

**Decision:** sorting needs a primary key or a unique index (the tie-breaker that makes the order total and stable); a table without one, and a materialized view (which is always read unordered), can be filtered and is paged by position as before.

**Why:** without a tie-breaker a page boundary can skip or repeat rows. The header says why a column cannot be sorted.

## 120. A hidden column can be neither sorted nor filtered until it is revealed

**Decision:** the adapter refuses a sort or a condition on a hidden column (every operator, even the null tests); the browser does not offer it; hiding a column again removes its filters and any sort on it.

**Why:** a condition on a column the viewer masked is an oracle: "starts with a", "starts with b" reads the secret one letter at a time without ever showing it. This is a security rule rather than a preference, and it is tested at every layer.

## 121. Text matching ignores case and has no wildcards; "does not equal" matches NULL; NULL goes where the database puts it

**Decision:** `contains` and `starts with` are `strpos(lower(...))` and `starts_with(lower(...))`, not `LIKE`, so `%`, `_` and `\` in a value are ordinary characters and nothing is escaped; equality is exact and typed (9 before 10, an enum in its declared order); "does not equal" is `IS DISTINCT FROM`; ascending sorts put NULL last and descending first.

**Why:** a person typing `50%` means those characters. A plain `<>` would drop every NULL silently, which is not what "not Ann" means. The database's own NULL placement lets a plain index serve a sort. A rule test fails on `LIKE`, `ILIKE`, `SIMILAR TO` or a regular-expression operator in the statement code.

## 122. Version 1.3.0, after 1.2.0; editing becomes 1.4.0

**Decision:** sort and filter, with a layout fix (the page itself could scroll with a long table list and leave a blank area under the canvas), are a minor version after the viewer's 1.2.0. The editing plan's suggested version moves from 1.3.0 to 1.4.0.

**Why:** each release stays small and the viewer's wording settles before it grows. Documents changed with the feature: the guide, the threat model, SECURITY.md and the README.

## 123. Version 1.4.0 also adds a table search in the sidebar

**Decision:** besides editing rows and designing tables, 1.4.0 includes a search box at the top of the sidebar's schema tree that narrows it to the tables and views whose name contains the text. It is planned in `docs/sidebar-table-search-plan.md` (T0) and independent of the editing milestones, so it can be built first.

**Why:** the tree loads one schema at a time, so finding a table means opening schemas and scrolling, and the only search (in the canvas toolbar) works on the canvas. Names only, no new route, and no change to what is read. Where the names come from is decision 136.

## 124. Editing changes rows (update, insert and delete) and designs tables (create and alter)

**Decision:** 1.4.0 lets a person update, insert and delete one row at a time, create a table from a form and alter an existing one, all without writing SQL. The client sends a structured operation; the server builds the statement from catalog-checked names, allow-listed types and defaults, and bound parameters. There is no SQL box, no bulk change, no import and no undo. **Full reasoning:** `docs/data-editing-plan.md`.

**Why:** requested on 2026-11-16 (the plan's S1 and S2). "No text typed by the user becomes SQL" stays true for writes, as it did for sort and filter (decision 116).

## 125. Writes need three independent switches: a start-up flag, a local database and a per-connection unlock

**Decision:** writes exist only when DataCanvas was started with `--enable-writes` (a flag, not an environment variable a person sets, so it shows in the command and the process list; the CLI passes it to the server internally); only on a connection whose host is loopback (`localhost`, `127.0.0.0/8`, `::1`); and only after the person unlocks that connection by typing its database name. The unlock lives in server memory, is never saved in a profile, and is cleared by disconnecting, reconnecting or restarting. Writing also needs data viewing to be on.

**Why:** a web page or a program holding the session token cannot reach a switch that is not in the API, and the typed name stops the wrong tab from being edited. "Local" is the host only, not the server's reported address: requiring a loopback server address would block every database in Docker or behind a port mapping, while a tunnel to production could still be made to look right. **Left over:** an SSH tunnel or the Cloud SQL Auth Proxy on `127.0.0.1` makes a remote database look local. The unlock dialog shows the address the server reports (`inet_server_addr()`), and a red "Writes on" badge stays visible, but neither is proof.

## 126. A warning when the database role can do more than the task needs

**Decision:** a read-only catalog query (`getRoleInfo`) reads whether the role is a superuser, can create roles or databases, bypasses row-level security, belongs to the predefined write or server-file roles, and on how many tables it can write. In read-only mode the app warns when the role can write at all; with writes unlocked it warns when the role can do far more than edit tables. It is information with a suggested fix, never a block.

**Why:** requested (S4). A read-only role is still the safest way to browse, and many people connect as a superuser without thinking about it. Some people legitimately use the owner of a local development database, so blocking them would be wrong.

## 127. Preview, then apply exactly what was previewed

**Decision:** every change is first previewed as the exact statement, its effect and its warnings, with a single-use id held in server memory for five minutes. Apply takes only that id. Each change is one transaction; a row change must touch exactly one row or it rolls back, and an update only applies if the changed columns still hold the values the person saw.

**Why:** the person sees what will run, and nothing different can run. The conflict check stops one person silently overwriting another's newer change.

## 128. Time limits for writes: 3 seconds to get a lock, 15 seconds for a row change, 60 seconds for a structure change

**Decision:** every write sets `lock_timeout` to 3 s; a row change has a 15 s `statement_timeout` and a structure change 60 s. One write runs at a time per connection.

**Why:** a change stuck behind a long transaction holds its own place in the lock queue and blocks every read after it. Failing fast with a clear message is better than quietly freezing someone's database.

## 129. Database errors from a write become fixed messages chosen by SQLSTATE

**Decision:** a failed write never shows PostgreSQL's own message. The SQLSTATE picks a fixed sentence, which may name a constraint or a column (structure) but never a value.

**Why:** PostgreSQL puts row values in its messages ("Key (email)=(a@x.test) already exists"), and the privacy rules say values never reach an error, a log or a file.

## 130. No CASCADE; drops are allowed but refused while anything depends on them

**Decision:** drop column and drop table ship in 1.4.0, behind the typed table name. A drop is refused when any view, foreign key or other object depends on it, and the refusal lists what does. No statement ever uses `CASCADE`.

**Why:** "alter" without drops is half a feature, and refusing on dependents keeps a drop from silently taking other objects with it.

## 131. The session history is kept in memory only and never holds values

**Decision:** the list of changes made since connecting holds the operation, the table, the column names, the time and the outcome (and the SQL for a structure change, except when the change carries a default value or a comment the person typed: that text is not kept). It is never written to a file. The preview shown to the person stays exact; only the history leaves such text out.

**Why:** a file would be one more thing to protect and document, for little gain.

## 132. Type changes only where PostgreSQL has a cast; no USING expressions

**Decision:** a column type change is offered only when `pg_cast` has an implicit or assignment cast from the old type to the new one. Anything that would need a `USING` expression is refused with an explanation.

**Why:** a `USING` clause is an arbitrary expression, which is the "no SQL typed by the user" line. A structured subset can come later.

## 133. No check constraints and no CREATE INDEX CONCURRENTLY in the first version

**Decision:** the table builder has no check constraints, and indexes are created with a plain `CREATE INDEX`, which takes a write lock (the preview says so).

**Why:** a check is an arbitrary expression. `CONCURRENTLY` cannot run inside a transaction, and every change here is one transaction.

## 134. Wording of the changed promises

**Decision:** the README, `SECURITY.md`, the threat model, the CLI help and start-up notice, the unlock dialog and the role warnings use the drafts in Appendix A of `docs/data-editing-plan.md`. "Read-only" becomes "read-only by default".

**Why:** a promise that is no longer true must not ship in the package (as for decision 115).

## 135. Version 1.4.0

**Decision:** editing and the sidebar table search ship together as 1.4.0, a minor version after sort and filter's 1.3.0.

**Why:** it adds features and changes a documented promise (read-only by default), with no breaking change to files or the command line.

## 136. The sidebar search loads every schema's table list once and filters in the browser

**Decision:** the first time the box is used, the table list of every schema is loaded (one request per schema, in parallel, through the same `loadAllTables` the overview uses), and the text is matched in the browser: case-insensitive, contains, with names that start with the text first. Views and materialized views are listed like tables. Columns are not searched (the canvas search does that), and there is no keyboard shortcut.

**Why:** filtering only the schemas that are open would miss the table the person is looking for, and the server's search route is capped and built for a dropdown. This way no new route is needed and the typed text never leaves the browser. Measured: on 5,011 tables in 50 schemas the first result appears in about 0.3 s and further typing in about 20 ms, so the fallback to the server's search was not needed (`e2e/performance.spec.ts`). **Left over:** the first keystroke on a very large database waits for the lists, and the box says so.

## 137. A preview only applies to the table it was made for

**Decision:** a plan records the identity of the tables and columns it names (the catalog object id, and the position of each named column). Applying takes a lock on each table first, then checks that identity before running anything, and refuses a stale plan: a row change with `row_changed`, a structure change with `invalid_change` ("The table changed since you previewed this ... Preview again"). Dropping a column is also refused while a generated column is computed from it. The guard pins identity: a plan that creates a table has nothing to pin, and a changed default or NULL setting on a column is not detected (since 1.5.2, a changed type, length or precision is: decision 139).

**Why:** a preview can wait up to five minutes. A table dropped and recreated under the same name in that time is a different table, and applying the old plan to it would change something the person never saw. Found in the review of the 1.4.0 pull request.

## 138. The migration file holds the structure changes of a session, and only those

**Decision:** "Export migration (.sql)" in the session history writes the changes of structure that were applied through the connection as one script in a `BEGIN`/`COMMIT`, in the order they ran. Row changes (insert, update, delete) are counted in a comment and never written. The full SQL of each applied structure change is kept in memory in a separate list, never in the history, so a default or a comment the person typed can be in the file but not in the history (decision 131 stands). Names in `--` comments are flattened to one line, because a quoted name may hold a line break. The file is built on the server and downloaded by the browser; nothing is saved to disk by DataCanvas.

**Why:** a migration is the way a change made by hand reaches other databases. Row values are exactly what decision 131 keeps out of every record, and data is not structure, so rows stay out. The history is shown on screen and sent often; the migration is asked for once, on purpose, by the person who typed the text.

## 139. A narrowing type change is destructive and says so

**Decision:** a type change that can round or cut values quietly is marked destructive and carries a `lossy` warning ("values may be rounded or cut"): an assignment cast other than between two integer types (numeric to integer, timestamptz to date), and a numeric column that keeps fewer decimals (`numeric(10,3)` to `numeric(10,2)`, which is the same type, so no cast is involved). A widening (implicit) cast is not, and neither is a narrowing between integer types, because an integer that does not fit is an error, not a quiet change. The plan guard of decision 137 also pins each named column's type as the database prints it, so a changed length or precision makes a plan stale. The cascade warning of a delete follows the chain of `ON DELETE CASCADE` keys to its end.

**Why:** PostgreSQL applies those casts without complaint, nothing undoes them, and the preview looked like any other. Found in the 1.5.2 review of the write path.

## 140. Writes need a session token

**Decision:** the writes switch is on only when the process was started with `--enable-writes` AND has a session token. The CLI always sets a token; a development server (`npm run dev`) has none, so writes stay off there.

**Why:** without a token only the Host check stands in front of the write routes. Found in the 1.5.2 review.

## 141. The SQL view runs read-only statements, one at a time, on a connection of its own

**Decision:** the SQL Workspace (1.6.0) runs the statement the person types inside a read-only transaction on a dedicated connection that is opened for that one run and closed after it, never on the pool. Several statements in one text are refused (the extended protocol is used), and writing is not offered even when `--enable-writes` is on. It needs "Table data" switched on for the connection. Column masking does not apply to its results. Details and the tests that guard each way out are in `docs/sql-workspace-plan.md`, section 3.

**Why:** until now no text typed by the person became SQL (decisions 116 and 127). A SQL view is exactly that, so it is the narrowest version that is still useful: a read-only transaction stops writes in the database itself, a connection of its own means a `SET SESSION` cannot change what a later write transaction does, and one statement per run means a `COMMIT` inside the text cannot end the transaction early and run the rest.

## 142. Monaco, with a curated list of features, loaded only when the SQL view opens

It is imported from `monaco-editor/editor/editor.api.js` plus a fixed list of features and the `pgsql` language, never from `monaco-editor` or `editor.main` (which register every language, the TypeScript, CSS, JSON and HTML services and a language-server client). The component that loads it is imported with `next/dynamic` and `ssr: false`, so it is in neither the first page nor the server bundle. The language `pgsql` supplies highlighting; completion comes from our own provider (plan section 4).

## 143. Completion in the SQL view is a pure function of the catalog, the text and the cursor

**Decision:** names are suggested from the structure the app already reads (`GET /structure`: schemas, tables and views with their columns and types, and function names with their arguments), turned into a small catalog held in memory per connection. It is read once when the SQL view opens, read again after a change of structure that DataCanvas itself applied, and dropped with the connection; it is never saved. What to suggest is decided by `complete(catalog, text, offset)` in `features/sql/completion/`: a tokenizer and a few rules, not a parser. It finds the statement the cursor is in, reads the relations of its FROM and JOIN clauses with their aliases (and CTEs), and suggests tables after FROM or JOIN, columns elsewhere, a relation's columns after `alias.`, and a schema's tables after `schema.`. A name it cannot resolve gives fewer suggestions, never an error; inside a string or a comment it gives none. Monaco's own word-based suggestions are off. No text is sent anywhere for completion.

**Why:** a parser for PostgreSQL's SQL would be a project of its own and would still fail on half-typed text, which is the only text completion ever sees. Rules over tokens degrade gracefully. Keeping it a pure function makes every rule a plain test (95 of them), and keeps Monaco out of the logic. **Left over:** a change made to the database by someone else is not seen until the view is opened again after the catalog is dropped (closing the connection); there is no refresh button yet. A relation named without a schema resolves to `public` first, because the search path is not known.
