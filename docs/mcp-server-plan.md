# Plan: 1.11.0, the MCP server ("connect Claude to the database you are connected to")

Status: **proposed 2026-11-24; the decisions of section 15 were taken by the owner on 2026-11-24 (every recommendation accepted; to be recorded in `docs/decisions.md` as decision 169, after 1.10.0's 161 to 168 land). Prioritised first: it comes before the write side's second part** (`docs/write-side-v2-plan.md`, which moves to 1.12.0). Written from the state of `main` at 1.9.0 with the 1.10.0 PR (#30) open; nothing here depends on 1.10.0 except where it says so (the statistics and the plan text are two more tools if it has landed).

## 1. What we promise

A person who has a database open in DataCanvas can let **Claude** (Claude Desktop, Claude Code, or any MCP client) **read it**: ask questions in plain words, get the schema explained, have Claude write and run **read-only** queries, and see the answers, all **without DataCanvas holding an API key, calling a cloud service or leaving a hole in the read-only guarantee**.

1. **An MCP server** that DataCanvas offers on its own local address, with a small set of **read-only tools** (list the connections you shared, schemas, tables, a table's columns, keys, indexes, relationships and statistics, run one read-only query, read a page of rows).
2. **A switch per connection, off by default, in memory only**: "Share with Claude", at one of two levels: **structure** (names, types, keys, statistics; no row) or **data** (read-only queries and rows too). It is never saved, never survives a restart, and needs the existing "Allow viewing table data" for the data level.
3. **You can see and stop everything**: a live **Claude activity** list (every tool call, the query text, how many rows came back), a **Pause** button, and an optional **approve each query** mode in which nothing runs until you press Approve.
4. **A one-line setup** for each client (a button that copies the exact config), through a **stdio bridge** (`datacanvas mcp`) that finds the running DataCanvas, so the token that changes on every run never has to be pasted into a config.
5. **The same limits as the SQL tab**: one statement at a time, a read-only transaction, row, size and time caps, hidden (sensitive-named) columns never returned, no value in any log.

What we do **not** promise: that data stays on your machine once Claude has read it (the Claude app you use sends what it reads to the model; DataCanvas cannot change that and says so every time you switch sharing on), **any write, ever** (there is no write tool, and the architecture tests keep it that way), an in-app chat or an API key (a later, separate decision, `docs/mcp-server-plan.md` section 14), or a server reachable from another machine or from claude.ai's cloud connectors (loopback only).

## 2. Why this design, and what it reuses

- **The data stays local until the client sends it.** The MCP server runs inside the DataCanvas process on `127.0.0.1`; the client (Claude Desktop, Claude Code) connects to it locally. DataCanvas makes no network call of its own and needs no key. What the model sees is what a tool returns, so **the tools are the privacy boundary**, which makes it small enough to design and test.
- **The connections are already open.** The person connected in the UI (the password is in server memory, never in a config file or a prompt). MCP uses **those** connections, so no credential is ever given to Claude or written for it.
- **The read-only machinery exists and is reviewed**: the SQL runner (`SqlService`, `checkStatementText`, a read-only transaction on a connection of its own, row, byte and time limits, cancel), the page reader (hidden columns, keyset paging, caps), the structure reads, the statistics. The MCP tools **call these services**; they add no new way to touch a database.
- **The guard exists**: Host check, no CORS, per-run random token, the `rows-gate` for data access. The MCP route needs a second kind of caller (a program that is not a browser), so it gets **its own token with a narrower scope** (section 5).

## 4. The tools (version 1)

All read-only, all with the MCP annotation `readOnlyHint: true`, `destructiveHint: false`, `openWorldHint: false`, each with a strict input schema (no free `sql` except in `run_readonly_query`).

| Tool                 | Level     | What it returns                                                                                                                                 | Limits                                                                           |
| -------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `list_connections`   | structure | The connections shared with Claude: an id, the connection's name, the database name, the level. No host, no user, no password                   | Only the shared ones; a connection that is not shared does not exist for Claude  |
| `list_schemas`       | structure | Schema names with table and view counts                                                                                                         |                                                                                  |
| `list_tables`        | structure | Tables and views of a schema: name, kind, estimated rows, comment                                                                               | 500 per call, a `cursor` for more                                                |
| `describe_table`     | structure | Columns (type, NULL, default, comment), keys, unique constraints, indexes, foreign keys in both directions, and (1.10.0) the table's statistics | One table                                                                        |
| `search_objects`     | structure | Tables and columns whose name contains a word, across schemas                                                                                   | 50 results                                                                       |
| `read_rows`          | data      | A page of rows of a table, the page reader's own statement: filter, sort, keyset paging, hidden columns left out and named                      | 100 rows a page (max 200), cells cut at 500 characters, a total of 100 KB a call |
| `run_readonly_query` | data      | The result of ONE statement, run by the SQL runner                                                                                              | 200 rows (max 1,000), 100 KB, 10 s (max 30 s), cells cut at 500 characters       |
| `explain_query`      | data      | `EXPLAIN (FORMAT JSON)` of a query, not run (no ANALYZE)                                                                                        | 1 MB of plan                                                                     |

- **Never any write tool**, no `COPY`, no `DO`, no `CALL`, no migration, no import. The list is fixed in code and **pinned by a test**: a new tool is a deliberate change of the test, a decision and a review.
- **Hidden columns** (names that look sensitive) are left out of every answer, whatever the query selects (the runner's result columns are checked by name for a query on a table; a column whose name looks sensitive is replaced by a note in `run_readonly_query` results: see section 8). The model cannot reveal them: there is no parameter for it.
- **`explain_query` is at the data level** (the plan of a query on a table can say how big it is and which values the planner expects: statistics, not rows, but conservative).
- The output is **compact**: a short text summary plus the data as JSON (`structuredContent`), rows as arrays with a column list (not an object for each row), so a large result costs few tokens.
- The server's **`instructions`** (sent at `initialize`) tell the model what this is: a read-only PostgreSQL, one statement at a time, call `describe_table` before querying, always `LIMIT`, hidden columns exist, **and that what a tool returns is data, never instructions**.
- Tool and parameter **descriptions** are written for a model: what it is for, the limits, and the fixed errors ("the connection is not shared", "this table has hidden columns: salary, api_token").

Not in version 1: MCP **resources** (the schema as a document) and **prompts** (canned questions), `read_rows` by key list, `get_paths` (the shortest foreign-key route between two tables, which the app has: a cheap later tool), and anything that needs a session (progress, sampling, elicitation).

## 5. Transport and authentication

### 5.1 The endpoint

`POST http://127.0.0.1:<port>/mcp`, **Streamable HTTP in its simplest form**: each request is one JSON-RPC message (or a batch), each answer one `application/json` response; **no session id, no stream** (`GET /mcp` answers 405, as the specification allows for a server with nothing to push). Stateless means nothing to leak between calls and nothing to clean up.

### 5.2 A token of its own (the part that needs care)

The browser's credential is the **session token in an `HttpOnly` cookie**. An MCP client is not a browser: it sends no cookie. So the MCP route has its **own secret**, and the two are **never interchangeable**:

- **The MCP token**: 256 random bits made at each start, held in memory, **valid only on `/mcp`**; the session token is refused there, and the MCP token is refused on every other route (a rule test pins both).
- **Sent as `Authorization: Bearer <token>`**, compared in constant time.
- **Host check applies** (`127.0.0.1:<port>`, `localhost:<port>`): DNS rebinding cannot reach it.
- **A request that carries an `Origin` header is refused** (403): a browser sends one, an MCP client does not. This is the specification's own advice for a local HTTP server, and it stops a web page from calling the endpoint even if it somehow learned the token.
- **Nothing is served at all** until the person has switched at least one connection to "shared": with none, `/mcp` answers 404, as if it did not exist.
- The token is written, for the bridge only, to **`~/.datacanvas/mcp.json`** (mode 0600, like `run.json`: the port and the token, deleted on clean shutdown, a stale file is useless because the token dies with the process).

### 5.3 The bridge (`datacanvas mcp`)

Claude Desktop starts a **command** and talks to it over **stdio**; Claude Code can do either. A token that changes at every run cannot be put in a config file. So `npx @shubhamtiwari909/datacanvas mcp` is a **tiny stdio bridge**: it reads `mcp.json`, forwards each line of JSON-RPC from stdin to `POST /mcp` with the bearer token, and writes the answers to stdout. It has no dependency, holds no secret of its own, and if DataCanvas is not running it answers a JSON-RPC error that says "Start DataCanvas, connect to your database and switch on Share with Claude" (plain words, not a stack trace). The config a person pastes never changes between runs:

```json
{
  "mcpServers": {
    "datacanvas": { "command": "npx", "args": ["--yes", "@shubhamtiwari909/datacanvas", "mcp"] }
  }
}
```

and for Claude Code: `claude mcp add datacanvas -- npx --yes @shubhamtiwari909/datacanvas mcp`. The setup dialog copies the right text for each.

## 6. The switch, the levels and the consent

- A **"Share with Claude"** control on each connection in the sidebar, next to "Table data" and "Writes". Off by default. **In memory only**: not in a profile, not in `connections.json`, gone on restart, disconnect, reconnect, or data viewing switched off (as the write unlock is).
- Turning it on opens a **dialog that says what happens**: which level (structure by default; data only if "Allow viewing table data" is on and the person ticks it), **"Anything Claude reads here is sent to Anthropic by the Claude app you use. DataCanvas cannot stop that or take it back."**, that it can read only (no write tool exists), what is never shown (columns whose names look sensitive), that **every call is listed and can be paused**, and a link to the setup.
- **The data level checks the role.** A database user that is a superuser (or can read files, `pg_read_server_files`) gets a warning that the read-only transaction does not stop what such a role can do outside it (the existing role notice), and the data level is **refused until the person ticks that they understand**, with the advice to use a read-only user. Structure-level sharing is not affected.
- **Approval mode** (off or on; **on by default for the data level**): a query or a read of rows **waits for the person to press Approve** in DataCanvas (showing the exact SQL text or the table and filters), with a time limit (2 minutes), after which the tool answers "not approved". One click on "Approve queries for this session" turns it off for the connection. Structure tools never ask.
- **Pause** stops every MCP call at once (tools answer "paused by the user") without ending the sharing.

## 7. The activity list

A **Claude activity** panel (a drawer opened from the sidebar, with a count badge while sharing is on): for each call, the time, the tool, the connection, **the statement text or the table and filters** (this is the model's request, shown to its owner), the outcome (rows returned, cut, refused, approved, not approved), and the size. **In memory, bounded to the last 200 calls, never written to a file or a log**, cleared with the sharing. It never holds a **returned value** (the rows came back to Claude, not to this list: it says "42 rows, 3.1 KB", not what they were). The statement text is the model's, which is shown to the person who allowed it; it can contain a literal the model wrote, which is why the list is memory-only like the SQL tab's history.

## 9. Quality of the answers

A server that is safe and useless is not worth shipping. The plan includes:

- **Tool descriptions and server instructions written and tested for a model**: a fixed set of 20 natural-language questions about a sample database (the shop fixture of the end-to-end tests) is run through the tools by a test client and checked for the right tool sequence; the descriptions are tuned until Claude Code and Claude Desktop use `describe_table` before querying (checked by hand in the spike, recorded in section 17).
- **Errors that teach**: "the column `emai` does not exist; did you mean `email`?" (the database's own hint), "this result was cut at 200 rows: add a LIMIT or a WHERE", "this table has a hidden column `api_token`".
- **Output size**: rows as arrays under a column list, numbers as text exactly as the database printed them (no float surprises), dates in ISO, at most 100 KB a call.

## 11. Tests

- **Protocol**: every JSON-RPC error code, a batch, a notification (no answer), an unknown method, a malformed body, a body over the limit, version negotiation with each of the versions the clients send; **the official SDK's client** (a dev-only dependency) calls the server over HTTP.
- **Tools**: each tool against a real PostgreSQL (versions 12 to 18 in CI): the happy path, the limits (rows, bytes, time, cells), a hidden column, a view, a partitioned table, a table without a key, awkward names (quotes, a line break), a refused statement, a statement that fails (the database's sentence returned, no value of ours).
- **Gates**: not shared / paused / data level off / data viewing off / role is a superuser: each answers as described and the same for "does not exist"; the approval flow with a timeout.
- **Security**: the session token is refused on `/mcp` and the MCP token on `/api`; a request with an `Origin` header is refused; a wrong Host is refused; `404` before anything is shared; constant-time comparison; the tool list equals the pinned list; no MCP file imports the write service; no `console` in the MCP files; the activity list holds a marker value of a returned row nowhere.
- **End to end** (Playwright and a spawned bridge): share a connection in the UI, an SDK client asks questions, the activity list shows them, Pause stops them, the bridge answers "start DataCanvas" when it is not running.

## 13. Risks of the project itself

- **The privacy promise changes in kind.** "Nothing leaves your machine" stays true of DataCanvas and stops being true of what a person does with a Claude app they connected to it. The product text must say exactly that, everywhere it says the old thing, and a rule test (like the one for the SQL tab) pins the wording.
- **Prompt injection cannot be solved here, only bounded.** The design bounds it (read-only, no other tool, limits, approval, the structure level) and says what it does not cover.
- **Client behaviour changes.** MCP clients and the specification move; the hand-written subset is small and tested against the official client, and the spike records the versions that exist today.
- **Hidden columns are a hint** (they already are in the data viewer): the model can ask a computed question about a column it cannot see. The role is the control; the dialog says so.
- **Scope creep.** An assistant invites an in-app chat, saved questions, charts and write tools. None is promised; each would be its own plan and its own decision (section 14).

## 14. After this release (not promised)

- **MCP resources and prompts** (the schema as a document, canned questions such as "find tables without a primary key").
- **`get_paths`, the Health findings and the Migrations plan as tools** (all structure-only, cheap to add, because the services exist).
- **An in-app assistant** with the person's own API key: a separate decision with its own consent screens, a per-request send confirmation, and its own review; the tools and the gates of this plan are what it would call.
- **A write tool** for the local, unlocked case: not planned. If it were ever built it would be its own release behind the three layers of `docs/data-editing-plan.md`, a preview and an approval for every change, and a review of the whole.

## 15. Decisions taken (2026-11-24): every recommendation accepted

1. **Hand-written protocol subset or the official SDK.** _Recommend_ a hand-written server (about 300 lines: the four methods, strict schemas, no runtime dependency, full control of limits and of what is logged), with **the official SDK as a dev dependency for the client in the tests**. The SDK as a runtime dependency brings an HTTP framework and many packages to a package that is 7 MB today and has no network code.
2. **Transport.** _Recommend_ stateless Streamable HTTP on `/mcp` plus the stdio bridge `datacanvas mcp` (section 5), loopback only.
3. **A token of its own for `/mcp`**, never the session token, refused elsewhere; a request with an `Origin` header refused. _Recommend_ exactly this.
4. **Where the MCP token is kept.** _Recommend_ `~/.datacanvas/mcp.json`, mode 0600, deleted on shutdown (the same class as `run.json`), because the bridge must find it.
5. **Levels.** _Recommend_ two: **structure** and **data**, structure the default, data needing "Allow viewing table data" and a tick in the dialog.
6. **Sharing is memory-only**, never saved with a profile, gone on restart or disconnect. _Recommend_ yes.
7. **Approval mode on by default for the data level**, one click to turn it off for a session. _Recommend_ yes; it is the best defence against a misled model and costs one click.
8. **Superuser or file-reading role at the data level**: refused until the person acknowledges, with the read-only-user advice. _Recommend_ yes.
9. **Hidden columns in `run_readonly_query`**: replaced by NULLs and named, and a query that names one is refused (section 8). _Recommend_ yes, said plainly to be a hint.
10. **Tool set of version 1** (section 4), with `explain_query` at the data level and no resources or prompts. _Recommend_ this set.
11. **Version.** _Recommend_ **1.11.0** for this, and the write side's second part becomes **1.12.0** (its plan and decisions stand unchanged).
12. **An independent review at the end**, as for every release that adds a door. _Recommend_ yes.
13. **Which clients to support and test.** _Recommend_ Claude Desktop (stdio) and Claude Code (stdio and HTTP) as supported, tested by hand in the spike and each release; any MCP client that speaks the protocol should work and is not promised.

## 15b. The decision as it will be recorded (decision 169)

**Decision (2026-11-24, `docs/mcp-server-plan.md`, section 15):** 1.11.0 is the **MCP server**, built before anything else; the write side's second part becomes 1.12.0 (its plan and decisions stand). DataCanvas serves a **hand-written subset of the protocol** (`initialize`, `tools/list`, `tools/call`, `ping`; no runtime dependency; the official SDK only as a dev dependency of the tests) as **stateless Streamable HTTP on `127.0.0.1/mcp`** plus the **stdio bridge `datacanvas mcp`**. The endpoint has **a token of its own** (never the session token, refused on every other route, and the session token refused on `/mcp`), **refuses any request that carries an `Origin` header**, applies the Host check, answers **404 until a connection is shared**, and keeps its token for the bridge in `~/.datacanvas/mcp.json` (mode 0600, deleted on shutdown). **Sharing is per connection, off by default, in memory only** (never in a profile, gone on restart, disconnect or data viewing switched off), at **two levels**: structure (the default) and data (which needs "Allow viewing table data" and a tick in the dialog that says what leaves the machine). **Approval mode is on by default for the data level** (a query or a read of rows waits for Approve, 2 minutes), with Pause and an in-memory **activity list** that never holds a returned value. **A superuser or file-reading role is refused at the data level until acknowledged.** **Hidden columns** are replaced by NULLs and named in `run_readonly_query`, and a query that names one is refused, said plainly to be a hint (the role is the control). The **tool set of version 1** is eight read-only tools, pinned by a test, with no write tool, no resources and no prompts. An **independent review** comes before the PR; Claude Desktop (stdio) and Claude Code (stdio and HTTP) are the supported clients.

**Why:** the data stays local until the client sends it, the connections are already open (no credential is given to Claude), and the read-only machinery is already built and reviewed, so the new surface is a protocol, a token and a switch: small enough to design, pin and test.

## 16. Open questions for the spike (M0)

- Does Claude Desktop start `npx` reliably on all three platforms (path, Windows `npx.cmd`), and how long does the first start take with the download? (If it is slow, the setup text should say to install the package globally and use `datacanvas mcp`.)
- Which protocol versions do Claude Desktop and Claude Code send at `initialize`, and what do they do when the server answers with another?
- Does either client reconnect after DataCanvas restarts (the token changes; the bridge re-reads `mcp.json` on every call, so it should).
- How do the clients show a tool error (`isError: true`) against a JSON-RPC error, and which gives the model the better message?
- How large a tool answer do they accept before they cut it?

## 17. What M0 found

Measured on 2026-11-24, with the real Claude Code (2.1.261) started with `--mcp-config` and `--strict-mcp-config` against the packaged app through the bridge (a logging wrapper between the client and the bridge recorded every line), and with the official SDK client (1.32.2) over HTTP and over stdio.

- **Claude Code sends `protocolVersion: "2025-11-25"`** at `initialize` (capabilities `roots` and `elicitation`, `clientInfo` `claude-code` 2.1.261), then `notifications/initialized`, then `tools/list`. The server answered the same version, and the handshake and the list worked through the bridge. (The model call that would have followed failed on this machine because the Claude login had expired, which has nothing to do with DataCanvas: **the tool call itself was verified with the official SDK client instead**; calling a tool from a live Claude Code session is a step of M7's hand test.) The SDK supports `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05` and `2024-10-07`; the server speaks the first four.
- **Node's own `fetch` sends `Sec-Fetch-Mode: cors`**, so the plan's rule "refuse any `Sec-Fetch-*` header" refused the bridge and the official client. The guard refuses `Origin` and `Sec-Fetch-Site` (a browser always sends them; Node does not) and does not look at the mode. Found by the first end-to-end run; a test pins that the two headers are the ones refused.
- **A tool's argument error is a tool result (`isError`), not a JSON-RPC error**, as the newer specification asks, so the model can correct itself; a tool that does not exist (or is not offered to this caller) is `-32602`. Both are tested, and an error never repeats a value.
- **Stateless works**: the official client accepts a server that answers every `POST` with one JSON body, answers `GET` with 405 and has no session id.
- **The setup text that works** for Claude Code is `claude mcp add datacanvas -- npx --yes @shubhamtiwari909/datacanvas mcp` (the stdio form, which is what was run here through `--mcp-config`); Claude Desktop's config is the JSON of section 5.3. Whether `npx` starts reliably on Windows and how long the first start takes is for M5's hand test on each platform.
- **Not measured yet:** the size of a typical tool answer (no data tool exists yet), how Claude Desktop shows a tool error, and whether either client reconnects after DataCanvas restarts (the bridge re-reads `mcp.json` on every message, so it should).

## 18. What M1 found

- **The package** (`packages/mcp`, about 300 lines) is pure: JSON-RPC 2.0, the four methods, strict schemas turned into JSON Schema by zod, answers that repeat nothing the client sent, a result larger than 200,000 characters refused instead of cut. An architecture rule keeps it free of any framework, network or database.
- **Two tokens, two scopes**: `DATACANVAS_MCP_TOKEN` is made by the CLI for each run (never the session token, and equal to it means `/mcp` does not exist), accepted only as `Authorization: Bearer` on `/mcp`, and written for the bridge to `mcp.json` (mode 0600, only the pid, the port and that token). The cookie guard never reads an `Authorization` header, so the token is no credential for the app (an end-to-end test sends it to `/api/connections` and is refused).
- **404 before anything is shared**, checked before the body is read, so a program that finds the port and has the token learns nothing.
- Sharing is `PUT /api/connections/:id/claude` (cookie-guarded, `off` / `structure` / `data`, memory only, the data level needs viewing table data and falls back to structure when it is switched off, a disconnect ends it).
- Only `list_connections` exists so far (M2 adds the structure tools).
